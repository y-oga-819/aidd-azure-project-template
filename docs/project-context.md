# プロジェクトの前提

このリポジトリ(プロジェクト)に固有の前提を、ここに集める。
ハーネス(skill、進め方の文書、テンプレート、`tools/`、`mise-tasks/`。範囲は [ハーネス](harness.md))は、固有の前提を自分の中に書かず、この文書の見出しを名前で指す。
ハーネスを別のリポジトリへ持ち出したときは、この文書だけを書き直せばよいようにするため。

- 書くこと: 技術とコードの置き場所、実行基盤と外部から届く口、レビューで疑う場所のように、プロジェクトが変われば変わること。
- 書かないこと: 判断の理由。理由は ADR に書き、ここからはリンクする。今の値(ポート番号など)も書かない。値はコードを見る。
- 見出しはハーネスから名前で指されている。見出しの名前を変えるときは `git grep -n "プロジェクトの前提" -- .claude docs` で指している箇所を探して直す。

## 何を作るか

Angular のフロントエンドと Python のバックエンドを、セキュアな構成で Azure 上に載せる検証用のプロジェクト。

## 技術とコードの置き場所

| 役割 | 技術 | 置き場所 |
| --- | --- | --- |
| バックエンド | Python | `backend/` |
| ドメイン(複雑な判断を集める純粋関数) | Python | `backend/src/app/domain/` |
| アプリケーション(協力者が多いコントローラー、API ハンドラ) | Python | `backend/src/app/application/` |
| バックエンドのテスト | pytest | `backend/tests/` |
| フロントエンド | Angular | `frontend/`(まだない) |
| インフラ | Bicep | `infra/` |

ドメインとアプリケーションの分け方は [テスト戦略](testing-strategy.md) の「コードの分類とテストの配分」に沿う。まだ無いディレクトリは、最初のコードを置くときに作る。

## 実行基盤と外部から届く口

- 実行基盤は Azure App Service(コンテナ)([ADR-0002](adr/0002-hosting-app-service.md))。
- 外部から届く口は Front Door だけで、アプリへの直接のアクセスは Azure Policy で拒否する([ADR-0003](adr/0003-single-public-entry.md))。Front Door を通ることは認証の代わりにならない。
- イメージは 1 つ、待ち受けのポートは 1 つ。番号はインフラの引数で渡す(今の値はコードを見る)。
- API は `/api` の下、それ以外は Angular の静的ファイルを返し、未知のパスは `index.html` を返す。Angular は API を相対パスで呼ぶ。
- シークレットは Key Vault に置き、コードや設定に書かない。インフラが守っていることの一覧は [Azure インフラのガードレール](../infra/docs/azure-infra-guardrails.md) にある。

## レビューで疑う場所

PR 概要で「該当なし」とされていても、次のファイルが変わっていれば該当する可能性が高い([レビューの観点](review-guide.md) の「人間が判断すべき変更」)。どのプロジェクトでも共通の場所(CI の定義、ロックファイルなど)はレビューの観点の側に書いてある。

| 変わったファイル | 当たる項目 |
| --- | --- |
| `infra/`、`*.bicep` | セキュリティ境界 |
| `backend/src/app/` の API のルーティングとスキーマ | 公開インターフェース |
