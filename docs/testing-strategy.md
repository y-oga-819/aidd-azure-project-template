# テスト戦略

『単体テストの考え方/使い方』(Vladimir Khorikov、原題 *Unit Testing Principles, Practices, and Patterns*)の古典学派の考え方に沿う。

このハーネスでは **テストコードが仕様の正本** になる(理由: [ADR-0005](adr/0005-tests-as-specification.md))。
そのため、テストは「動作を守る」だけでなく「仕様として読める」ことも求める。

## 1. 前提にする考え方

- テストは資産ではなく負債。価値の高いものだけを持つ。
- 価値は 4 本の柱で測る: **退行に対する保護、リファクタリングへの耐性、迅速なフィードバック、保守のしやすさ**。
- リファクタリングへの耐性は譲らない。**観察可能な振る舞いだけを検証し、実装の詳細は検証しない。**
- 単位は「コード」(クラスやメソッド)ではなく「振る舞い」。隔離するのはテスト同士であり、協力者ではない。

## 2. コードの分類とテストの配分

テスト戦略が設計を決める。複雑な判断はドメインの純粋関数に集め、外部とのやり取りはコントローラーに寄せる(関数型コア / 命令型シェル、Humble Object)。

| 分類 | 置き場所 | テスト |
|---|---|---|
| ドメイン・アルゴリズム(複雑、協力者が少ない) | ドメイン層 | **単体テスト** で網羅する(出力値ベース) |
| コントローラー(協力者が多い、ロジックは薄い) | アプリケーション層、API ハンドラ | **統合テスト** |
| 取るに足らないコード | DTO、マッピング、設定 | テストしない |
| 過度に複雑なコード | — | 書かない。上の 2 つに分割する |

各層がこのプロジェクトのどのディレクトリかは、[プロジェクトの前提](project-context.md) の「技術とコードの置き場所」にある。

フロントエンドは表示と操作に徹し、**業務ルールを持たない**。料金や可否の判定はバックエンドが正本で、二重に実装しない。
表示用の小さなロジックだけを単体テストし、画面は E2E を主要な導線に数本だけ置く。

## 3. テストの層と責務

| 層 | 確かめること | 依存の扱い |
|---|---|---|
| 単体 | ドメインのルール。境界値と組み合わせはここで網羅する | 依存なし(純粋関数) |
| 統合 | ビジネスシナリオごとに **最長のハッピーパスを 1 本**。加えて、単体では確かめられない異常系(DB 制約、トランザクション、外部依存の失敗、冪等性) | 管理下の依存(自分のアプリだけが使う DB)は本物を使う。管理外の依存(決済代行、メール、外部 API)だけをモックにし、モックはシステム境界の一番外側に置く |
| E2E | 主要なユーザー導線が通るか | 全部本物(外部はサンドボックス) |

スタイルの優先順位は **出力値ベース > 状態ベース > コミュニケーションベース(モック)**。

## 4. 組み合わせが増えたときの方針

入力の直積でテストしない。ケース数を「掛け算」から「足し算」にする。

1. **判断を独立した小さな関数に分ける。** 例えば送料・割引・税は別の関数にし、それぞれの中だけで網羅する。
2. **種類で分岐するものは先に切り出す。** 決済方法ごとに型や関数を分け、その中でパラメータ化する。
3. **パラメータ化は「仕様上意味のある組み合わせ」ごとに 1 ケースにする。** 「どちらでもよい」条件は展開しない。境界値はそのケースの中で足す。
4. **1 つのパラメータ化テストの軸は 2 つまで。** 3 つ要るなら、ドメインの分け方が足りないサインと考える。
5. **期待値の形が同じものだけを 1 つの表にまとめる。** 成功と失敗は分ける。
6. **部品同士の相互作用は、名前の付いたテストにする**(例: クーポンを税率区分ごとに按分する)。暗黙の組み合わせに頼らない。
7. **部品を合成した全体の正しさは、計算例で確かめる。** 代表的な 2〜3 例を、期待値をハードコードして単体テストにする。
8. **状態遷移は例外として、状態 × イベントの全マスを網羅してよい。** 全マスが仕様であり、1 ケースが一瞬で終わるため。状態が 10 を超えたら状態機械を分けることを検討する。
9. **値だけが変わる改定(料金の改定など)はロジックを複製しない。** ロジックのテストは 1 回だけ書き、値は引数(設定)で渡す。版の選択だけを境界値でテストする。

どの組み合わせを残し、どれをまとめたかは、計画の「テストケースの洗い出し」に書いて人間がレビューする([開発の進め方](development-flow.md))。

## 5. 書き方の規約

テストが仕様として読めるための約束。

- **テスト名は振る舞いを平易な日本語で書く。** メソッド名を入れない。
  - 良い: `test_遠隔地のゴールド会員は閾値未満なら送料が半額になる`
  - 悪い: `test_calc_shipping_fee_gold`
- **why はテストの docstring に 1〜2 行で書く。** なぜそのルールなのかは、テストからは読み取れないため。
- **テスト ID を書く。** 計画・PR 概要・テストを結ぶ。
  - パラメータ化テスト: `pytest.param` の id の先頭に書く(例: `id="LOTTERY-3 応募が枠を超えたら枠の数だけ当選"`)
  - それ以外: docstring の 1 行目に ID だけを書く(例: `"""ORDER-8"""`)
  - 書けているかは `mise run docs:spec` で確かめる。ID のないテストは「(ID なし)」と表示される
  - 番号は機能ごとの連番。次の番号は `mise run test:next-id <接頭辞>` で出す(他のブランチが使っている番号も避ける)
  - 重複と書き漏れ(ID のないテスト)は `mise run check`(`test:ids`)と CI で落ちる。重複したら、後からマージする側が振り直す([ADR-0010](adr/0010-test-id-numbering.md))
  - pytest は `-v` の表示で日本語の id を `\uXXXX` にエスケープするが、表示だけの問題で、`docs:spec` は元の文字に戻して扱う
- **テスト ID の接頭辞は、機能の正式な名前を略さずに書く**(例: `ORDER-1`、`LOTTERY-3`、`SHIPPING-2`)。`ORD` のような略語は、読む人が何の略か分からないため使わない。
- **パラメータには `pytest.param(..., id="…")` で意味のある id を付ける。** id が仕様一覧の行になる。パラメータ名(引数名)は計画の表の列名に揃える。`plan:verify` は列名が一致する列の値を照合する。
- AAA(Arrange / Act / Assert)で書く。テストの中に if やループを書かない。
- **期待値はハードコードする。** テストの中でドメインの計算を再実装しない。
- モックは管理外の依存にだけ使う。スタブとのやり取りは検証しない。
- 時刻と乱数は引数で渡す(テストで固定できるようにする)。
- カバレッジは目標にしない。大きく下がったときの警告としてだけ使う。

```python
@pytest.mark.parametrize(
    ("地域", "小計", "ランク", "期待する送料"),
    [
        pytest.param(Region.本州等, 5_000, Rank.一般, 0, id="SHIPPING-1 本州等は閾値以上なら無料"),
        pytest.param(Region.本州等, 4_999, Rank.一般, 600, id="SHIPPING-2 本州等の一般会員は閾値未満なら600円"),
        pytest.param(Region.本州等, 4_999, Rank.ゴールド, 0, id="SHIPPING-3 本州等のゴールド会員は閾値未満でも無料"),
    ],
)
def test_基本送料は地域と小計と会員ランクで決まる(地域, 小計, ランク, 期待する送料):
    """SHIPPING-1〜3

    ゴールド会員(年会費あり)の継続率を上げるため、本州等は無料にしている。
    """
    assert base_shipping_fee(地域, 小計, ランク) == 期待する送料
```

## 6. テストの質を機械で確かめる

| 手段 | 何を捕まえるか | いつ |
|---|---|---|
| CI のテスト実行(`mise run check`) | 振る舞いの退行 | すべての PR |
| ミューテーションテスト | テストが実装の誤りを本当に検出できるか(期待値が甘い、ケースが抜けている) | **任意実行。** PR で変更したモジュールだけを対象にする。実行するかは人間が決める。ドメインの計算ロジックを変えた PR では実行を推奨する |

ミューテーションテストは、実装をわざと少し壊したもの(ミュータント)を作り、テストが落ちるかを見る。落ちなかったミュータントが「生存」で、テストが検出できない実装の誤りを表す。

```sh
mise run test:mutation         # 既定ブランチから変更したファイルだけ
mise run test:mutation --all   # 全体(時間がかかる)
```

- CI では、PR に `mutation-test` ラベルを付けると動く(`.github/workflows/mutation.yml`)。Actions の画面から手動でも実行できる
- 生存またはテストなしのミュータントがあると失敗する。生存したものは、そのコンポーネントのディレクトリ(例: `backend`)で `uv run mutmut show <名前>` を実行すると、どう壊したかが分かる。テストを足すか、意味のない変化(ログの文言など)なら受け入れる
- ツールは Python が mutmut。TypeScript(フロントエンド)は Stryker を候補とし、フロントエンドを作るときに `test-mutation` タスクを足す
