# ADR-0010: テスト ID は機能ごとの連番のままにし、重複は機械で止めて後からマージする側が振り直す

- 状態: 採用（2026-11-17）
- 関連: [ADR-0005](0005-tests-as-specification.md)、[ADR-0009](0009-gate1-draft-pr.md)、[テスト戦略 5 章](../testing-strategy.md)、[重複の検出](../../tools/src/aidd_spec/ids.py)、[次の番号を出すタスク](../../mise-tasks/test/next-id)

## 背景（なぜ決める必要があるか）

テスト ID（`ORDER-8` など）は、計画・PR 概要・テストを結ぶ（テスト戦略 5 章）。これまでは「`docs:spec` で今の最大の番号を見て、その続きにする」と決めていた。
4〜5 人で並行すると、同じ機能の別のストーリーを 2 人が同時に計画し、両方が同じ番号を取る。

この重複は、次の理由で人も機械も気づけなかった。

- 別のファイルや別の位置に足された同じ ID は、git がコンフリクトせずにマージする。
- 同じ位置に足してコンフリクトしても、解消はふつう「両方残す」なので、重複は残る。
- `plan:verify` は同じ ID のテストが 2 つあると、テスト名が一致した方で照合して通す（[verify.py](../../tools/src/aidd_spec/verify.py)）。
- マージした計画は書き換えない（ADR-0007）ので、計画に書かれた ID がどちらのテストを指すか、後から分からなくなる。

採番の方式に求めること:

1. ID が読みやすいこと。仕様一覧（`docs:spec`）の行として人が読む。
2. 重複が main に入らないこと。
3. 採番のたびに手間が増えないこと。
4. GitHub から Azure DevOps に移っても同じ方式でよいこと。

## 選択肢

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. 連番のまま、重複を機械で止める（採用）** | 採番の時点で他のブランチが使っている番号も避け、すり抜けた重複は CI で落とす | ID が短く読みやすい。今のテストと計画をそのまま使える | 重複を作りの上では防げない。すり抜けたら後の PR が計画・テスト・PR 概要の ID を振り直す |
| B. ストーリーの番号を ID に入れる（`ORDER-42-3` など） | Issue やワークアイテムの番号で名前空間を分ける | 作りの上で重複しない。ID から元のストーリーをたどれる | ID が長くなる。Issue の番号に依存し、Azure DevOps へ移ると番号の体系が変わる。今の ID の形（接頭辞の後は英字）を変える必要がある |
| C. ID を予約するファイルを main に置く | 採番のたびに小さな PR で予約する | 衝突は予約ファイルのコンフリクトとして必ず見える | 採番のたびに PR が 1 つ増える |

## 決定

**A を採用する。** 次の 3 段で重複を止める。

1. **採番の時点で避ける。** 次の番号は、手元と origin の全ブランチのテストと計画を見て出す（`mise run test:next-id <接頭辞>`）。ADR-0009 で計画をドラフトの PR として先に出すので、他の人が計画中の番号もここで見える。
2. **手元で止める。** テスト ID の重複と書き漏れ（ID のないテスト）を `mise run check` で検出する。`mise run pr` は push の前に check を流す。
3. **CI で止める。** CI は PR と main への push の両方で check を流す。PR の CI は作った時点の main と比べるだけなので、相手が先にマージすると素通りすることがある。そのときも main で落ちるので、すぐ気づける。

すり抜けた重複は、**後からマージする側** が振り直す。直すのは計画・テスト・PR 概要の ID の置き換えだけで、AI に任せれば手間は小さい。

決め手は、4〜5 人なら同じ機能の同時採番はまれで、衝突したときの振り直しも安いこと。B の「作りの上で重複しない」利点より、ID の読みやすさと、移行で番号の体系が変わらないことを優先した。

## 結果（この判断で受け入れること）

- 番号が飛ぶことがある（他のブランチが取ったまま閉じた、書き方の例と同じ番号を避けた、など）。飛びは害がないので詰めない。
- 手元の検査は、まだ push されていない他人の作業を見られない。採番の時点で避けられるのは、計画を push 済みのブランチだけ。
- PR の CI が古い main と比べて通ることがある。マージ前にブランチを最新にすることを必須にすれば塞げるが、まだ設定していない。main で落ちたら、後からマージした側がすぐ振り直す。

## 確かめ方

- `mise run test:ids`（check に含む）が、重複と ID のないテストで失敗する。

## 見直しの条件

- 振り直しが月に何度も起きる → B（ストーリーの番号を ID に入れる）を検討する
- main で重複が見つかり、気づくまでに他の PR が積み重なった → マージ前にブランチを最新にすることを必須にする
