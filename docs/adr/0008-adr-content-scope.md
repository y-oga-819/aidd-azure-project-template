# ADR-0008: ADR の決定は判断と約束に絞り、決めないことと前提の事実の根拠を書く

- 状態: 採用（2026-11-16）
- 関連: [ADR の運用ルール](README.md)、[ADR-0006](0006-adr-operation.md)（決めた時点の記録にする）、[ADR のテンプレート](../templates/adr.md)、[PR レビューの観点](../review-guide.md)、[参考にした記事: ADR を書くためのガイドライン](https://zenn.dev/tokium_dev/articles/adr-authoring-guideline)

## 背景（なぜ決める必要があるか）

ADR-0006 で、ADR は決めた時点の記録にし、進み具合・今の値・PR の経緯を書かないと決めた。
これは「時間とともに変わること」を外す線引きで、決定の節に **何をどこまで書くか** は決めていない。

AI が ADR を下書きする前提で、次のことが起きうる。

1. **決定に実装の細部が入る。** ファイル名、環境変数名、設定のキーなどは、実装を少し変えるだけで古くなる。ADR はマージ後に書き換えないので、古くなった記述が残り続ける。
2. **前提の事実が確かめられないまま残る。** 料金の目安や、ある機能の制約など、AI はもっともらしい誤りを書くことがある。前提が誤っていると判断も誤るが、根拠がないとレビューで裏を取れない。
3. **決めていない隣の論点が、決まったように読める。** 決めないことを本文の途中に書くと見落とされ、委譲先が辿れない。

他社の事例として、AI が書いた ADR で同じ 3 つが起き、レビュー指摘から作った規約で防いでいる記事がある（関連のリンク）。ただしその規約は 34 本の PR、830 件のレビュー指摘から作られている。このリポジトリの実例はまだ少ない。

満たしたいことは、ADR-0006 と同じく「後から読んだ人が当時の判断を正しく読める」「保守が軽い」こと。加えて、書き手（AI）とレビュアーが同じ基準を見ること。

## 選択肢

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. 運用ルールに 3 つを足し、各ルールに判定の問いを添える（採用）** | 「実装の細部」を書かないことに足し、「前提の事実の根拠」「決めないこと」を書くことにする。ルールは README に 1 か所だけ置き、レビューの観点からは参照する | 今あるルールの表に行を足すだけで済む。判定の問いがあると、AI も人も迷いにくい | ルールが増え、README が長くなる。規約の名前がないので、レビュー指摘が長くなる |
| B. A に加え、規約に ID と強さ（MUST / SHOULD）を振る | 記事と同じ形にする | レビューで「D-1 に反する」と短く指摘できる。AI レビューの根拠に使いやすい | 実例が少ないうちに作ると、机上の規約が増える。記事自身も、規約は繰り返されたレビュー指摘から作るべきとしている |
| C. ADR の一覧を README に置き、状態の変化に合わせて保つ | 記事の「一覧を追従させる」に倣う | どれが有効か一目で分かる | 一覧と各 ADR の状態の行が二重になり、ずれる。今は 8 本でファイル一覧で足りる |
| D. 何も足さず、レビューで都度指摘する | 今の運用のまま | ルールが増えない | 同じ指摘を毎回人間がすることになり、AI の下書きも直らない |

## 決定

**A を採用する。** 運用ルールは [docs/adr/README.md](README.md) に書き、テンプレートとレビューの観点はそこを参照する。要点は次のとおり。

- **決定には判断と約束だけを書き、実装の細部を書かない。** 判定の問いは「実現の方法を別の方法に替えたら、本文を書き換える必要があるか」。必要なら、それは実装の細部で、コードと PR 概要の「この PR だけの判断」に置く。コードの場所は「関連」にリンクする。
- **前提の事実には根拠を添える。** 判断を左右する事実に限り、公式ドキュメントや確かめたコードへのリンクを添える。確かめていなければ「推測」と書く。
- **決めないことがあれば、「この ADR で決めないこと」の節に、いつ・どこで決めるかと一緒に書く。** Issue の番号では書かない。Azure DevOps へ移ると Issue のリンクが切れるので。

既存の ADR は、運用ルールが許す範囲（リンク、意味を変えない言い回し、見出しの表記）だけを直す。足りない節を足したり、決定にある実装の細部を消したりはしない。中身の変更になり、決めた時点の記録でなくなるので。

## 結果（この判断で受け入れること）

- ADR の決定から、どのファイルを触ればよいかは直接は読めない。「関連」のリンクを辿る。
- 根拠を添える分、書くのが少し重くなる。
- 既存の ADR には、今のルールで書かないこと（決定の中のファイル名など）が残る。

## 批判的な再検討

- **「実装の細部を外すと、ADR が抽象的になって役に立たなくならないか」**
  約束（「API は `/api` の下に置く」「外部から届く口は 1 か所に列挙する」）は判断なので書いてよい。外すのは、その約束をどのファイルのどのキーで実現したか、だけ。それは「関連」のリンクで辿れ、リンクはマージ後も直してよい。
- **「規約 ID がないと、AI レビューに組み込みにくいのでは」**
  その通りで、AI レビューを CI に入れるときには ID が欲しくなる。そのときに、実際に繰り返された指摘から ID を振る（見直しの条件）。
- **「根拠を求めても、AI がそれらしいリンクを捏造するのでは」**
  ありうる。だからリンクを添えさせ、レビューで開いて確かめられるようにする。根拠がないことを「推測」と書かせることで、確かめるべき箇所が分かる。
- **「ルールより前の ADR を直さないと、悪い例として AI が真似るのでは」**
  ありうる。テンプレートと README のルールを AI が読む導線（プランニング skill、テンプレートのコメント）で防ぐ。それでも真似る例が繰り返されたら、README に「古い ADR は書き方の手本にしない」と書く。

## 見直しの条件

- AI レビューを CI に入れることになった → 繰り返された指摘から、規約に ID と強さを振る（案 B）
- 同じ指摘がレビューで 3 回以上繰り返された → その指摘をルールに足す
- 「関連」のリンク切れや、根拠のリンク先の誤りが繰り返し見つかった → 機械で検査する
