# ADR-0008: ADR の決定は判断と約束に絞り、反論への答えは各節に書く

- 状態: 採用（2026-11-16）
- 関連: [ADR の運用ルール](README.md)、[ADR-0006](0006-adr-operation.md)（決めた時点の記録にする）、[ADR のテンプレート](../templates/adr.md)、[PR レビューの観点](../review-guide.md)、[参考にした記事: ADR を書くためのガイドライン](https://zenn.dev/tokium_dev/articles/adr-authoring-guideline)、[MADR](https://adr.github.io/madr/)、[Nygard: Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

## 背景（なぜ決める必要があるか）

ADR-0006 で、ADR は決めた時点の記録にし、進み具合・今の値・PR の経緯を書かないと決めた。
これは「時間とともに変わること」を外す線引きで、決定の節に **何をどこまで書くか** と、**どの節を持つか** は決めていない。

AI が ADR を下書きする前提で、次のことが起きうる。

1. **決定に実装の細部が入る。** ファイル名、環境変数名、既定値などは、実装を少し変えるだけで古くなる。ADR はマージ後に書き換えないので、古くなった記述が残り続ける。
   実際に、ADR-0003 の決定にあった待ち受けポートの既定値（80）を、コンテナを root 以外で動かすために 8080 へ変える計画で、「ADR を書き換えるか、新しい ADR で置き換えるか」の迷いが出た。判断（ポートを 1 つにする）は変わっていないのに、本文に値があるせいで ADR を触りたくなった。
2. **前提の事実が確かめられないまま残る。** 料金の目安や、ある機能の制約など、AI はもっともらしい誤りを書くことがある。前提が誤っていると判断も誤るが、根拠がないとレビューで裏を取れない。
3. **決めていない隣の論点が、決まったように読める。** 決めないことを本文の途中に書くと見落とされ、委譲先が辿れない。
4. **反論への答えが、他の節と重なる。** テンプレートに「批判的な再検討」の節があり、「捨てた案の方が良いのでは」には選択肢と、「この短所は大丈夫か」には結果と、同じことを 2 か所に書いていた。この節は、結論を批判的に見直すという作業の手順を、そのまま記録の形にしたもので、代表的な ADR の形（Nygard、MADR）にはない。

他社の事例として、AI が書いた ADR で 1〜3 が起き、レビュー指摘から作った規約で防いでいる記事がある（関連のリンク）。ただしその規約は 34 本の PR、830 件のレビュー指摘から作られている。このリポジトリの実例はまだ少ない。

また、AI は既存の ADR を書き方の手本にする。ルールを足しても、既存の ADR が古い書き方のままだと、ルールより悪い例の方が強く効く（1 の実例も、既存の ADR に値があったことから起きた）。
今ある ADR-0001〜0007 は 2026-11-14〜15 に書いたもので、決めた人の記憶が新しく、古い版を前提にした文書もまだ少ない。

判断の基準は、ADR-0006 と同じく「後から読んだ人が当時の判断を正しく読める」「保守が軽い」こと。加えて、書き手（AI）とレビュアーが同じ基準を見ること。

## 選択肢

### 書く範囲のルール

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. 運用ルールに足し、各ルールに判定の問いを添える（採用）** | 「実装の細部」を書かないことに足し、「前提の事実の根拠」「決めないこと」「反論への答えの置き場所」を書くことにする。ルールは README に 1 か所だけ置き、レビューの観点からは参照する | 今あるルールの表に行を足すだけで済む。判定の問いがあると、AI も人も迷いにくい | ルールが増え、README が長くなる。規約の名前がないので、レビュー指摘が長くなる |
| B. A に加え、規約に ID と強さ（MUST / SHOULD）を振る | 記事と同じ形にする | レビューで「D-1 に反する」と短く指摘できる。AI レビューの根拠に使いやすい | 実例が少ないうちに作ると、机上の規約が増える。記事自身も、規約は繰り返されたレビュー指摘から作るべきとしている |
| C. ADR の一覧を README に置き、状態の変化に合わせて保つ | 記事の「一覧を追従させる」に倣う | どれが有効か一目で分かる | 一覧と各 ADR の状態の行が二重になり、ずれる。今は 8 本でファイル一覧で足りる |
| D. 何も足さず、レビューで都度指摘する | 今の運用のまま | ルールが増えない | 同じ指摘を毎回人間がすることになり、AI の下書きも直らない |

### 「批判的な再検討」の節

| 案 | 長所 | 短所 |
| --- | --- | --- |
| **節をなくし、反論への答えを選択肢・決定・結果に書く（採用）** | 同じことを 2 か所に書かない。代表的な形（Nygard、MADR）に近く、外の人も読みやすい | 反論を考えることを、節の存在で強制できなくなる |
| 節を残す | 反論を Q&A の形で読める。AI に反論を考えさせる強制力がある | 選択肢・結果と重なる。考える手順が記録の形に紛れ込む |

反論を考えること自体は、計画（プランニング skill）と PR のレビューの段階で行う。ADR には、その答えだけを残す。

### 既存の ADR

| 案 | 長所 | 短所 |
| --- | --- | --- |
| **一度だけ、判断を変えずに書き方を揃える（採用）** | AI が手本にする例が、ルールと一致する。決めた人の記憶が新しいうちにできる | ADR-0006 の「マージ後は中身を書き換えない」に一度だけ例外を作る。移すときに後付けの理屈が混ざるおそれがある |
| 直さず、新しい ADR からルールを効かせる | ADR-0006 を一切曲げない | 古い書き方が手本として残り、1 の実例のような迷いが続く |
| 悪い例として真似されたら、その都度直す | 必要な分だけ直す | すでに真似が起きている。後になるほど、決めた人の記憶が薄れる |

## 決定

**書く範囲は A、「批判的な再検討」の節はなくす、既存の ADR は一度だけ揃える。** 運用ルールは [docs/adr/README.md](README.md) に書き、テンプレートとレビューの観点はそこを参照する。

- **決定には判断と約束だけを書き、実装の細部を書かない。** 判定の問いは「実現の方法を別の方法に替えたら、本文を書き換える必要があるか」。必要なら、それは実装の細部で、コードと PR 概要の「この PR だけの判断」に置く。コードの場所は「関連」にリンクする。
- **前提の事実には根拠を添える。** 判断を左右する事実に限り、公式ドキュメントや確かめたコードへのリンクを添える。確かめていなければ「推測」と書く。
- **決めないことがあれば、「この ADR で決めないこと」の節に、いつ・どこで決めるかと一緒に書く。** Issue の番号では書かない。Azure DevOps へ移ると Issue のリンクが切れるので。
- **反論への答えは、答えが属する節に書く。** 捨てた案の方が良いという反論は選択肢の短所と決定の決め手に、採用した案の短所は結果に、その対策は決定の約束に。
- **任意の節「確かめ方」を足す。** 決定が守られていることを何で確かめるか（Policy、CI、テスト、レビュー）。機械検証を重んじるこのリポジトリの進め方に合わせる（MADR の Confirmation に相当）。
- **ADR に書かれた実装の細部だけが変わるときは、新しい ADR を起こさず、ADR も書き換えない。** 判断は変わっていないので。変えた理由は PR 概要の「この PR だけの判断」に書く。
- **ADR-0001〜0007 は、この ADR と同じ PR で一度だけ書き方を揃える。** 揃えるのは、反論の答えを各節へ移す、実装の細部を外して「関連」のリンクにする、本文に散らばった決めないことを節に移す、前提の事実に根拠を添える、の 4 つ。選んだ案、決め手、受け入れたことは変えない。足りない節（確かめ方、見直しの条件）は、もとの本文にある内容から起こし、新しい理由は足さない。この例外はこの一度に限り、以後は ADR-0006 のとおりマージ後に書き方を直さない。

## 結果（この判断で受け入れること）

- ADR の決定から、どのファイルを触ればよいかは直接は読めない。「関連」のリンクを辿る。これはリンクがマージ後も直せることで成り立つ。
- 約束（「API は `/api` の下に置く」「外部から届く口は 1 か所に列挙する」）は判断なので書いてよい。外すのは、その約束をどのファイルのどのキーで実現したか、だけ。ADR が抽象的になりすぎないよう、この線を守る。
- 根拠を添える分、書くのが少し重くなる。AI がそれらしいリンクを捏造するおそれもあるので、レビューでリンクを開いて確かめる。確かめていない事実は「推測」と書かせ、確かめるべき箇所を見えるようにする。
- 規約に ID がないので、AI レビューを CI に入れるときに不便になる。そのときに、実際に繰り返された指摘から ID を振る（見直しの条件）。
- 既存の ADR を揃えるとき、後付けの理屈が混ざるおそれがある。新しい理由は足さず、もとの本文にある内容を移すだけにし、決めた人がレビューで「当時もそう考えていたか」を確かめる。
- 「一度だけの例外」が前例になるおそれがある。README にこの一度に限ると書き、以後の書き直しはレビューで止める。

## この ADR で決めないこと

- ADR の書き方を機械で検査するか（見出しの有無、状態の行の形など）。検査を足すかは、ルール違反が繰り返されたときに決める（見直しの条件）。
- ADR 以外の文書（skill、計画、テスト戦略など）での章番号による参照。この ADR のルールは ADR だけが対象で、他の文書の書き方はそれぞれの文書を直すときに決める。

## 確かめ方

- 機械では確かめない。PR のレビューで、[レビューの観点](../review-guide.md) から README のルールを参照して確かめる。

## 見直しの条件

- AI レビューを CI に入れることになった → 繰り返された指摘から、規約に ID と強さを振る（案 B）
- 同じ指摘がレビューで 3 回以上繰り返された → その指摘をルールに足す
- 「関連」のリンク切れや、根拠のリンク先の誤りが繰り返し見つかった → 機械で検査する
- 反論を考えずに書かれた ADR（捨てた案の短所が書かれていない、受け入れる短所がない）がレビューで繰り返し見つかった → 「批判的な再検討」の節を戻すことを検討する
