# ADR-0005: 仕様の正本をテストコードにし、計画は使い捨てにする

- 状態: 採用（2026-11-14）
- 関連: [テスト戦略](../testing-strategy.md)、[開発の進め方](../development-flow.md)、[計画テンプレート](../templates/plan.md)

## 背景(なぜ決める必要があるか)

AI がコードの大半を書く前提で、人間は「なぜ」と「どう動けば正しいか(受け入れ条件)」を守る。
チームで並行して開発するので、次を満たすドキュメントの体系が必要になる。

1. **今の正しい振る舞いが 1 か所にあること。** 古い文書を根拠に AI や人が作業しないため。
2. **コードとずれないこと。** ずれたら機械が気づける形にする。
3. **保守の手間が小さいこと。** 重い仕様書は続かない。チームは以前、ユーザーストーリー → 仕様書 → レビューで進めた経験があり、仕様書の保守が重かった。
4. **並行開発でコンフリクトしにくいこと。**

また、受け入れ条件を読むのはエンジニアと AI だけで、開発者以外は読まない見込み。納品用の設計書は後から書き起こすことがあるが、決まった形式はない。

## 選択肢

| 案 | 正本 | 評価 |
| --- | --- | --- |
| A. ストーリーごとの仕様書を保守し続ける | 仕様書 | 同じ機能の文書が積み重なり、どれが最新か分からなくなる。保守が続かない |
| B. Wiki やチケットに置く | Wiki | コードとずれても誰も気づかない |
| C. Gherkin(`.feature`)を実行可能な仕様にする | `.feature` | コードとずれれば CI が落ちる。ただしステップ定義の保守が重い。開発者以外が読まないので、利点(誰でも読める)が活きない |
| D. 機能ごとの README にルール表・決定表を置き、ID でテストと結ぶ | README + テスト | 試し書きしたところ、README の表とテストの期待値が二重管理になった。型に合わない複雑さ(料金の改定など)で文書の形が歪んだ |
| **E. テストを正本にし、表は変更時の計画にだけ書く(採用)** | テスト | テストは常にコードと一致する。表は計画の中で人間のレビューに使い、マージで役目を終える |

## 決定

**仕様の正本はテストコードにする。** テスト戦略([testing-strategy.md](../testing-strategy.md))に沿い、テスト名・パラメータの id・docstring の why で、テストを仕様として読めるようにする。

あわせて、次の役割分担にする。

| 文書 | 寿命 | 中身 |
| --- | --- | --- |
| 計画(`docs/templates/plan.md`) | 使い捨て。ストーリーと PR に紐づけ、マージ後は更新しない | why、テストケースの洗い出し(決定表や状態遷移表など網羅の根拠)、質問と回答、テストケース一覧、PR の分割 |
| テスト | 恒久(正本) | 振る舞い。docstring に why |
| 機能ごとの README(`docs/templates/feature-readme.md`) | 恒久。薄く保つ | テストからは読み取れないことだけ: 目的、対象外、用語、関連、処理の順序 |
| ADR(`docs/adr/`) | 恒久 | PR より長く効く判断と、捨てた案 |
| PR 概要(`docs/pull_request_template.md`) | PR ごと | 計画から該当部分を引き写す |

仕様の一覧や納品用の設計書が欲しいときは、テストから **生成** する。手で保守しない。

## 結果(この判断で受け入れること)

- **テストの読みやすさにすべてが乗る。** テスト名やパラメータの id が雑だと、仕様が読めなくなる。書き方の規約(testing-strategy.md の 5 章)を守り、AI のレビューで確かめる。
- **今の仕様の全体像は、生成しないと見えない。** テストから一覧を生成するタスク(`docs:spec`)と、計画のテストケース一覧とテストを照合するタスク(`plan:verify`)が必要になる。
- **計画が大きくなりうる。** 小さな変更では、計画の「テストケースの洗い出し」を省略してよいとする。
- **設計がテスト戦略に縛られる。** 複雑な判断をドメインの純粋関数に分けていないと、この進め方は成り立たない。
- PR テンプレートの受け入れ条件の表にある「ルール ID(機能ごとの README のルール表と揃える)」は、この決定と合わないので見直す必要がある。
