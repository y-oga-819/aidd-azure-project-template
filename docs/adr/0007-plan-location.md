# ADR-0007: 計画はリポジトリの docs/plans/ に置き、テストと同じブランチでコミットする

- 状態: 採用（2026-11-15）
- 関連: [ADR-0005](0005-tests-as-specification.md)、[開発の進め方](../development-flow.md)、[計画テンプレート](../templates/plan.md)、[プランニング skill](../../.claude/skills/planning/SKILL.md)

## 背景（なぜ決める必要があるか）

ADR-0005 で、計画は使い捨て（ストーリーと PR に紐づけ、マージ後は更新しない）と決めた。ただし、計画のファイルをどこに置くかは決めていない。
プランニング skill が計画を書き出すので、置き場所を 1 つに決める必要がある。

置き場所に求めること:

1. **`mise run plan:verify <計画>` で照合できること。** 照合はファイルのパスを受け取る。
2. **PR 概要からリンクでき、マージ後もリンクが切れないこと。** 作業ブランチはマージ後に消すので、ブランチの URL は切れる。
3. **人間のゲート 1 でレビューしやすいこと。**
4. **古い計画が、今の仕様の根拠として読まれないこと。** ADR-0005 の背景にある「どれが最新か分からなくなる」問題を繰り返さないため。
5. GitHub から Azure DevOps に移っても、同じ置き場所を使えること。

## 選択肢

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. リポジトリの `docs/plans/`（採用）** | 作業ブランチでテストと一緒にコミットする | `plan:verify` にそのまま渡せる。マージ後は既定ブランチの URL で残る。差分と行コメントでレビューできる。プロバイダーに依存しない | ファイルが溜まり続ける。古い計画を AI が今の仕様と取り違えるおそれがある |
| B. Issue やワークアイテムの本文 | ストーリーの本文に計画を書く | ストーリーと一体で、リポジトリが散らからない | `plan:verify` に渡すにはファイルへの書き出しが要り、本文と二重になる。行単位のレビューがしにくい。移行時に Boards へ移す必要がある |
| C. リポジトリの外（共有フォルダ、Wiki） | 計画を別の場所に置く | リポジトリが散らからない | コードとの対応が取れず、リンクも切れやすい。照合に取り込む手間が要る |
| D. A に置き、マージ後に消す | 役目を終えたら消す | 溜まらない、取り違えない | PR 概要からのリンクが切れる。消す手間と消し忘れが出る |

## 決定

**A を採用する。** 計画は `docs/plans/<ストーリーの短い英語名>.md` に置き、テストや実装と同じ作業ブランチでコミットする。

あわせて次の約束を置く。

- マージした後の計画は更新しない。続きの変更は新しい計画にする。
- `docs/plans/` は経緯の記録であり、今の仕様の根拠にしない。今の仕様は `mise run docs:spec` でテストから引く。これを `docs/plans/README.md` とプランニング skill に書き、人と AI の両方に伝える。

## 結果（この判断で受け入れること）

- `docs/plans/` のファイルは増え続ける。一覧が読みにくくなっても、整理のために書き換えない。
- 古い計画を読んだ AI が誤る余地は残る。防ぐのは README と skill の注意書きだけで、機械では止めていない。

## 批判的な再検討

- **「使い捨てなのにリポジトリに残すのは矛盾しないか」**
  使い捨ては「マージ後に保守しない」の意味で、「消す」ではない。保守しない文書を残しても、正本（テスト）と取り違えなければ害は小さい。PR 概要から引ける履歴として残る利点の方が大きい。
- **「AI が古い計画を読んで誤るのではないか」**
  起こりうる。ADR と同じく「決めた時点の記録」として読む約束にした。誤りが実際に起きたら、`docs/plans/` を AI の検索対象から外す（設定で除外する）などの機械的な対策を検討する。
- **「Issue に置く方が Azure DevOps の Boards と相性がよいのでは」**
  ストーリーそのものは Issue やワークアイテムに置き、計画はそこからリンクする。照合とレビューのしやすさを優先した。

## 見直しの条件

- 古い計画を今の仕様と取り違えた誤りが実際に起きた → 除外の設定、または D（マージ後に消す）を検討する
- `docs/plans/` が大きくなり、リポジトリの扱いに支障が出た → 年ごとのディレクトリに分ける、または外に移す
