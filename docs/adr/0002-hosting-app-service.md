# ADR-0002: アプリの実行基盤に Azure App Service を採用する

- 状態: 提案（2026-11-14）
- 関連: [ADR-0003](0003-single-public-entry.md)、[infra/docs/guardrails.md](../../infra/docs/guardrails.md)

## 背景（なぜ決める必要があるか）

Angular（フロントエンド）と Python（バックエンド）を Azure 上で動かす。基盤に求めることは次のとおり。

1. **閉域にできる**: アプリも依存先（Key Vault、将来の DB）もパブリックネットワークに出さない。入口は Front Door (WAF) だけ。
2. **シークレットを持たない**: マネージド ID で他のリソースに接続でき、シークレットは Key Vault 参照で渡せる。
3. **ガードレールを Azure Policy で書ける**: 「パブリックアクセス禁止」などを組み込みポリシーで Deny できる。
4. **確実に動く**: テンプレートとして、最初の実デプロイでつまずきにくい。
5. **運用とコストが重すぎない**。

## 選択肢

| 案 | 長所 | 短所 |
| --- | --- | --- |
| **A. App Service（採用）** | Front Door + Private Link + App Service は定番構成で、**チームに既存の構築実績がある**。Python / Node の実行環境が組み込みでコンテナ不要（ACR が要らない）。1 つのプランに web と api を相乗りできる | 0 台まで縮められず、アクセスが少なくてもプラン代がかかる。TLS・FTP・基本認証などの組み込みポリシーは Deny を選べず監査のみ |
| B. Container Apps | 使った分だけの課金で、0 台まで縮められる。web と api を同じコンテナの仕組みで扱える。外部公開の禁止を Deny で書ける | イメージを置く ACR（閉域なら Premium、月 50 ドル程度）が必要。Front Door から内部モードの環境への Private Link は新しい構成で、実績がない |
| C. Static Web Apps + Functions | フロントの配信が簡単 | 閉域化の選択肢が少なく、Python API の自由度が低い |
| D. AKS | 何でもできる | 運用負荷が大きく、テンプレートの目的に対して過剰 |

## 決定

**A. App Service を採用する。**

当初は B（Container Apps）で書いたが、レビューで次の 2 点から A に切り替えた。

- **既存の Front Door + App Service 構成の実績に乗れる**（要件 4）。B で最も不確かだった「Front Door → 閉域アプリの Private Link」が、A では動いた実績のある組み合わせになる。
- **コストに決定的な差がない**（要件 5）。固定費の大半は両案共通の Front Door Premium。アプリ部分は、低トラフィックなら B、常時負荷がある本番なら A がやや有利で、A は ACR が不要な分だけ固定費が下がる。

## 批判的な再検討

- **「Deny できないポリシーが増え、ガードレールが弱くなったのでは？」**
  一部は弱くなった。TLS・FTP・基本認証・マネージド ID は AuditIfNotExists しか選べないので、
  IaC 側（`app-service.bicep`）で設定し、Policy は崩れていないかの監査に使う。
  一方、最も重要な「アプリに直接届かない」（`publicNetworkAccess`）は Deny できるので、G1 の強さは変わらない。
- **「web にもランタイム（Node）を持たせるのは無駄では？」**
  静的ファイルの配信だけなら Storage の静的サイトや Static Web Apps もある。ただし閉域にした Front Door 経由の構成が増えると、
  ガードレールも 2 系統になる。web と api を同じプラン・同じポリシーで扱えることを優先した。
- **「デプロイ経路の問題（閉域だと GitHub ホストランナーから届かない）は解決したか？」**
  解決していない。App Service でも SCM サイトが閉域になるため同じ問題が残る。アプリの CD を作るときに決める（guardrails.md 7 章）。

## 見直しの条件

- アクセスが少ない環境が増え、プランの固定費が目立つようになった → B（0 台まで縮められる）を再検討
- コンテナ前提の依存（ネイティブライブラリ、独自ランタイム）が必要になった → App Service のコンテナ機能か B を検討
