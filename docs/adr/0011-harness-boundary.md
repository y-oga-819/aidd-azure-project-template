# ADR-0011: ハーネスはこのリポジトリで育てて固有の前提を 1 つの文書に集め、他のリポジトリへは zip で配って最初のコミットで取り込む

- 状態: 採用（2026-11-17）
- 関連: [ハーネス](../harness.md)、[配るファイルの一覧](../harness-files.txt)、[取り込んだ後のセットアップ](../../scripts/harness-init.sh)、[プロジェクトの前提](../project-context.md)、[一覧の検査](../../mise-tasks/harness/files)、[zip にまとめるタスク](../../mise-tasks/harness/pack)、[ADR-0004](0004-task-runner-mise.md)

## 背景（なぜ決める必要があるか）

進め方の文書、skill（プランニング、PR 前の理解度テスト）、補助ツール（aidd_spec）、mise のタスク、それを決めた ADR（以下まとめてハーネス）は、このリポジトリで作ってきた。
ハーネスはこのリポジトリ専用ではなく、他のリポジトリへ持ち出して使えるものとして育てたい。

ところが、ハーネスの中にこのプロジェクトの前提が混ざっていた。

- プランニングの観点の一覧に「このリポジトリの前提」として Front Door、App Service、Angular の配信の仕方が書かれていた。
- テスト戦略とレビューの観点に `backend/src/app/domain/`、`infra/`、`*.bicep` のような場所が書かれていた。
- backend の仕様収集のタスクが、ハーネスのツールを `../tools/src` という相対パスで読んでいた。

このまま持ち出すと、持ち出した先で skill がこのプロジェクトの前提で質問の仮の答えを作る。どこを書き換えればよいかも、ファイルを読んで探すしかない。

境界の引き方に求めること:

1. 持ち出した先で書き換える場所が少なく、どこかが分かること。
2. 今の開発の速さを落とさないこと。利用先はまだこのリポジトリ 1 つで、ハーネスは使いながら毎週のように変わっている。
3. 他のリポジトリへ持ち出すのが簡単なこと。持ち出した先で中身が独自に分かれていくのは、当面は受け入れる。

## 選択肢

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. このリポジトリの中で境界を引く（採用）** | 固有の前提を 1 つの文書に集め、ハーネスはその見出しを指す。配るファイルの一覧を 1 か所に置く。切り出しは 2 つ目の利用先が来たとき | ハーネスの変更とその試用が同じ PR で済む。持ち出すときは一覧と前提の文書だけを見ればよい | 境界は約束で守るだけで、ハーネスの文書に固有の前提が戻っても機械では気づけない |
| B. 今すぐハーネス専用のリポジトリに切り出す | ハーネスを別リポジトリに移し、このリポジトリは Copier などで取り込む | 境界がリポジトリの境目になり、崩れようがない | ハーネスを直すたびに 2 つのリポジトリで PR が要る。利用先が 1 つのうちは、何を汎用にすべきかの手がかりも 1 つしかなく、汎用化の形を早く決めすぎる |
| C. ハーネスのファイルを 1 つのディレクトリに集める | `harness/` の下に移し、境界をディレクトリで表す | 一覧が要らない | skill の置き場所（`.claude/skills/`）、PR テンプレートの置き場所（`docs/`、[README](../../README.md) の末尾）、mise のファイルタスクの置き場所はツールが決めているので、集めきれない |
| D. 何もしない | 持ち出すときに考える | 今の手間はない | 固有の前提が増え続け、持ち出すときに全部の文書を読み直すことになる |

配り方の選択肢:

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **ア. zip（採用）** | 配る範囲を zip にまとめ、使う側の最初のコミットで取り込む | 使う側に道具が要らない。取り込みが一番簡単 | 後からの更新は手で差分を取り込む。使う側ごとに中身が分かれる |
| イ. [Copier](https://copier.readthedocs.io/) | このリポジトリをテンプレートにして取り込み、更新も取り込む | 取り込んだ版が記録され、更新を 3-way マージで取り込める（公式ドキュメントによる。この ADR では試していない） | 使う側に Copier（Python）が要る。テンプレートとしての設定と、版のタグ付けを保つ手間がある |
| ウ. git submodule / パッケージ | ハーネスを別リポジトリやパッケージにして参照する | 更新が一番楽 | B と同じく、今すぐ切り出す必要がある。skill や PR テンプレートの置き場所はツールが決めているので、参照だけでは置けない |

## 決定

**A と、配り方はアを採用する。** 次の約束を置く。

- プロジェクトに固有の前提は、プロジェクトの前提の文書にだけ書く。ハーネスの文書と skill は、その見出しを名前で指す。
- 配る範囲は一覧の 1 か所で決める。一覧は、そのまま配るものと、利用先で用意するもの（プロジェクトの前提、ルートの mise の設定）を分ける。利用先で用意するものは、取り込むときに利用先の既存のファイルを上書きしない。一覧のパスが実在するかは check で確かめる。
- zip には、元にした版（コミット）と、利用先で用意するファイルと、入れたファイルの一覧を入れる。中身が分かれた後でも、どの版から来たかで元と見比べられるようにする。
- コンポーネントがハーネスの置き場所を知らずに済むよう、ハーネスの場所はルートの設定 1 か所で決める。
- ハーネスが前提にする技術（テストは pytest、タスクは mise、VCS は GitHub か Azure DevOps、文書は日本語、エージェントは Claude Code）は、汎用化の対象にせず、ハーネスの立場として明記する。外すと作り直しになる範囲も書いておく。

決め手は、利用先が 1 つのうちは B の「崩れようがない境界」の利点より、ハーネスを直して試すまでの速さが大きいこと。汎用にすべき形は 2 つ目の利用先で初めて分かるので、そこまでは境界を引いて持ち出せる状態にしておくだけにとどめる。
配り方は、使う側で中身が分かれるのを当面は受け入れるので、更新の仕組み（イ、ウ）の利点より、取り込みの簡単さを取った。範囲を一覧にしておけば、後でイに替えるときも一覧をそのまま使える。

## 結果（この判断で受け入れること）

- 持ち出すときは、zip を展開してセットアップのスクリプトを流し、プロジェクトの前提を書けばよい。利用先に mise の設定が既にあれば、手でまとめる。
- 持ち出した先との間で、改善が自動では行き来しない。こちらの改善を取り込むのも、向こうの改善を持ち帰るのも、差分を見て手で行う。
- 境界が崩れても機械では気づけない。ハーネスの文書に「このリポジトリでは〜」と固有の前提が戻るのを、レビューで見る。
- ハーネスの ADR とこのプロジェクトの ADR が、同じ連番を使い続ける。持ち出した先では番号が飛んで見える。
- ハーネスの立場に挙げた技術を使わないプロジェクトには、そのままでは持ち出せない。

## この ADR で決めないこと

- ハーネスを別のリポジトリに切り出すか。見直しの条件で決める。
- 持ち出した先での ADR の番号の付け方。最初に持ち出すときに、持ち出した先で決める。
- 境界が崩れていないかを機械で確かめるか。下の見直しの条件で決める。

## 確かめ方

- `mise run harness:files`（check に含む）が、一覧のパスが無くなったら失敗する。
- ハーネスの文書と skill に固有の前提が書かれていないかは、レビューで見る。

## 見直しの条件

- 持ち出した先へ改善を手で取り込むのが重くなった、または分かれた中身を揃えたくなった → イ（Copier）に替える
- 利用先が 2 つ以上になり、ハーネスを直す PR の多くがこのプロジェクトのコードを触らなくなった → B を考える
- ハーネスの文書や skill に固有の前提が戻るのが、レビューで 2 回以上見つかった → 機械の検査を足すか、B を考える
