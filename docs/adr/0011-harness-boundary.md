# ADR-0011: ハーネスは Angular / Python / Azure を前提にこのリポジトリで育てて zip で配り、zip に入れるものは、このリポジトリに置いていくものを参照しない

- 状態: 採用（2026-11-17）
- 関連: [ハーネス](../harness/README.md)、[配るファイルの一覧](../harness/files.txt)、[取り込んだ後のセットアップ](../../scripts/harness-init.sh)、[プロジェクトの前提](../project-context.md)、[一覧の検査](../../mise-tasks/harness/files)、[zip にまとめるタスク](../../mise-tasks/harness/pack)、[ADR-0004](0004-task-runner-mise.md)

## 背景（なぜ決める必要があるか）

進め方の文書、skill（プランニング、PR 前の理解度テスト）、補助ツール（aidd_spec）、mise のタスク、それを決めた ADR（以下まとめてハーネス）は、このリポジトリで作ってきた。
ハーネスはこのリポジトリ専用ではなく、他のリポジトリへ持ち出して使えるものとして育てたい。

ハーネスの中には、このプロジェクトの構成が具体的に書かれている。

- プランニングの観点の一覧に、Front Door、App Service、Angular の配信の仕方が書かれている。
- テスト戦略とレビューの観点に `backend/src/app/domain/`、`infra/`、`*.bicep` のような場所が書かれている。
- backend の仕様収集のタスクが、ハーネスのツールを `../tools/src` という相対パスで読んでいる。

一方で、この具体名こそが観点の効き目になっている。観点は「気づくきっかけ」を並べたもので、AI も若手も「Front Door のキャッシュ」「Angular の `index.html`」のような具体名から見落としに気づく。「CDN など」「本番の環境」のようにぼかすと、きっかけにならない。
持ち出す先は、同じ Angular / Python / Azure の構成で作るチームのリポジトリを想定している（推測。まだ 2 つ目の利用先は無い）。

境界の引き方に求めること:

1. skill と文書の具体さ（気づくきっかけ）を落とさないこと。
2. 持ち出した先で書き換える場所が少なく、どこかが分かること。
3. 今の開発の速さを落とさないこと。利用先はまだこのリポジトリ 1 つで、ハーネスは使いながら毎週のように変わっている。
4. 他のリポジトリへ持ち出すのが簡単なこと。持ち出した先で中身が独自に分かれていくのは、当面は受け入れる。

| 案 | 内容 | 長所 | 短所 |

| **A. 技術を前提にし、リポジトリごとの違いだけを分ける（採用）** | Angular / Python / Azure の構成をハーネスの立場（想定する構成）に入れ、skill と文書は具体名で書く。何を作るか、想定する構成と違う点、ガードレールの場所だけを 1 つの文書に分ける。配るファイルの一覧を 1 か所に置く | 具体さを落とさない。ハーネスの変更とその試用が同じ PR で済む。持ち出すときは一覧と前提の文書だけを見ればよい | 違う構成のプロジェクトには、そのままでは持ち出せない。構成が少し違うだけでも、観点の具体名を読み替える手間がある |

## 決定

**A と、配り方はアを採用する。** 次の約束を置く。

- ハーネスは Angular / Python / Azure の構成を前提にし、その形をハーネスの文書に「想定する構成」として書く。skill と文書はその具体名で書き、ぼかさない。その構成を採るかの技術選定はプロジェクトの判断なので、プロジェクトの ADR に書き、ハーネスには入れない。
- ハーネスの判断も、このリポジトリの ADR に今までどおり 1 本の連番で積む（甲）。ADR は zip に入れない。
- zip に入れるものは、このリポジトリに置いていくもの（ADR、アプリとインフラのコード、プロジェクトの文書）を参照しない。理由が要るところは、配る文書の中に 1〜2 文で書く。参照していないことは check で確かめる。
- リポジトリごとに違うこと（何を作るか、想定する構成と違う点、ガードレールの場所）だけを、プロジェクトの前提の文書に書く。skill は計画の材料としてこれを読み、違う点があれば観点を読み替える。
- このリポジトリのアプリとインフラの中身はハーネスに入れない。
- 配る範囲は一覧の 1 か所で決める。一覧は、そのまま配るものと、利用先で用意するもの（プロジェクトの前提、ルートの mise の設定）を分ける。利用先で用意するものは、取り込むときに利用先の既存のファイルを上書きしない。一覧のパスが実在するかは check で確かめる。
- zip には、元にした版（コミット）と、利用先で用意するファイルと、入れたファイルの一覧を入れる。中身が分かれた後でも、どの版から来たかで元と見比べられるようにする。
- コンポーネントがハーネスの置き場所を知らずに済むよう、ハーネスの場所はルートの設定 1 か所で決める。
- ハーネスが前提にする技術（Angular / Python / Azure、テストは pytest、タスクは mise、VCS は GitHub か Azure DevOps、文書は日本語、エージェントは Claude Code）は、汎用化の対象にせず、ハーネスの立場として明記する。外すと作り直しになる範囲も書いておく。

ADR を配らない決め手は、持ち出した先のプロジェクトの ADR が自分の技術選定から始まり、配る文書がそれだけで読めること。使う側に要るのはルールで、理由はハーネスを育てる側が持てば足りる。乙の「持ち出した先でも理由が読める」利点より、配る文書が ADR に依存しない単純さを取った。配らないなら持ち出した先の番号には影響しないので、このリポジトリの中まで丙のように分ける必要はない。
境界の引き方の決め手は、E の「どこにでも持ち出せる」利点より、観点の具体さが大事なこと。ハーネスの価値は気づきを促すところにあり、ぼかした観点は効かない。持ち出す先も同じ構成を想定している。
B を取らないのは、利用先が 1 つのうちは「崩れようがない境界」の利点より、ハーネスを直して試すまでの速さが大きいため。汎用にすべき形は 2 つ目の利用先で初めて分かるので、そこまでは境界を引いて持ち出せる状態にしておくだけにとどめる。
配り方は、使う側で中身が分かれるのを当面は受け入れるので、更新の仕組み（イ、ウ）の利点より、取り込みの簡単さを取った。範囲を一覧にしておけば、後でイに替えるときも一覧をそのまま使える。

## 結果（この判断で受け入れること）

- 持ち出すときは、zip を展開してセットアップのスクリプトを流し、プロジェクトの前提（何を作るか、想定と違う点）を書けばよい。利用先に mise の設定が既にあれば、手でまとめる。
- 持ち出した先との間で、改善が自動では行き来しない。こちらの改善を取り込むのも、向こうの改善を持ち帰るのも、差分を見て手で行う。
- 境界が崩れても機械では気づけない。ハーネスにこのリポジトリのアプリやインフラの中身（今の値、ファイルの中身）が入り込むのを、レビューで見る。
- 想定する構成は、ハーネスの文書とプロジェクトの技術選定の ADR の両方に書かれる。構成を変えるときは両方を見直す。
- ハーネスの立場に挙げた技術を使わないプロジェクトには、そのままでは持ち出せない。観点やテスト戦略の具体名を書き直すことになる。

## この ADR で決めないこと

- ハーネスを別のリポジトリに切り出すか。見直しの条件で決める。
- 境界が崩れていないかを機械で確かめるか。下の見直しの条件で決める。

## 確かめ方

- `mise run harness:files`（check に含む）が、一覧のパスが無くなったとき、配るファイルが zip に入らないファイルへリンクしたとき、ADR の番号を書いたときに失敗する。
- ハーネスにこのリポジトリの中身が入り込んでいないかは、レビューで見る。

## 見直しの条件

- 持ち出した先へ改善を手で取り込むのが重くなった、または分かれた中身を揃えたくなった → イ（Copier）に替える
- 利用先が 2 つ以上になり、ハーネスを直す PR の多くがこのプロジェクトのコードを触らなくなった → B を考える
- ハーネスにこのリポジトリの中身が入り込むのが、レビューで 2 回以上見つかった → 機械の検査を足すか、B を考える
- Angular / Python / Azure 以外の構成のリポジトリに持ち出したくなった → その構成の分だけ観点を足すか、E のように抽象化するかを、効き目を確かめながら考える
- 持ち出した先で「なぜこうなっているのか」の問い合わせが繰り返し来る → 配る文書に理由を足すか、乙（ADR も配る）を考える
