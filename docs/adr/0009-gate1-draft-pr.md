# ADR-0009: 計画のレビュー（ゲート 1）は、計画だけを載せたドラフトの PR で行う

- 状態: 採用（2026-11-17）
- 関連: [ADR-0005](0005-tests-as-specification.md)、[ADR-0007](0007-plan-location.md)、[開発の進め方](../development-flow.md)、[プランニング skill](../../.claude/skills/planning/SKILL.md)、[計画の照合タスク](../../mise-tasks/plan/verify-changed)、[CI](../../.github/workflows/ci.yml)

## 背景（なぜ決める必要があるか）

開発の進め方では、コードを書く前に人間が計画をレビューする（ゲート 1）。計画の誤りは、テストや実装を書いた後より、今直す方が安いため。
ADR-0007 で計画はテストや実装と同じ作業ブランチに置くと決めたが、ゲート 1 を **どこで、どう記録して** 行うかは決めていなかった。
このままだとレビュアーが計画を目にするのは PR を開いたときで、そのときにはテストも実装もできている。4〜5 人で並行すると、計画の段階で他の人の目が入らない。

ゲート 1 の場に求めること:

1. コードを書く前に、作成者以外が計画を読み、行単位で指摘できること。
2. ゲート 1 を通ったことが記録に残ること。
3. 計画のテストケース一覧とテストの照合（`plan:verify`）を CI で必ず通せること。ただし、計画だけの段階ではテストがまだ無いので、照合は落ちるのが正しい。
4. 計画が使っているテスト ID が、他の人から見えること（[ADR-0010](0010-test-id-numbering.md) の採番で避けるため）。
5. GitHub から Azure DevOps に移っても同じやり方ができること。

## 選択肢

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. 同じブランチでドラフトの PR を先に開く（採用）** | 計画だけをコミットしてドラフトの PR を開き、レビューを受けてから同じ PR にテストと実装を積む。レビューに出すときにドラフトを外す | 行コメントでレビューできる。計画とテストと実装が 1 つの PR にまとまり、ADR-0007 のままでよい。ドラフトかどうかで照合を流すかを切り替えられる。開いた時点で計画の ID が他の人に見える | PR が長く開く。ドラフトの間にもらった承認が、そのまま実装の承認に見えるおそれがある |
| B. 計画だけの PR を作ってマージし、別の PR で実装する | 計画を先に main に入れる | ゲート 1 の記録が「マージ」で明確 | PR が 2 つに分かれ、計画と実装の対応が切れる。マージ後の計画を書き換えない約束（ADR-0007）と、実装中に計画を直したい場面がぶつかる |
| C. PR の外（チャット、Issue のコメント、口頭）でレビューする | 計画ファイルのリンクを渡して見てもらう | 手軽 | 行単位の指摘がしにくい。記録が散らばる。他の人から計画の ID が見えない |
| D. ゲート 1 を置かない | 実装の PR でまとめてレビューする | 一番速い | コードを書いた後に計画の誤りが見つかり、書き直しになる。開発の進め方の前提が崩れる |

## 決定

**A を採用する。** 計画ができたら、計画だけをコミットしてドラフトの PR を開き（`mise run pr --draft`）、ゲート 1 のレビューを受ける。その後、同じ PR にテストと実装を積み、レビューに出すときにドラフトを外す。

決め手は、ADR-0007（計画とテストは同じブランチ）を変えずに、行単位のレビューと記録と ID の見える化が全部手に入ること。B は記録が明確だが、計画と実装の対応が切れる短所の方が大きい。

あわせて次の約束を置く。

- **ゲート 1 の通過は、レビュアーのコメントで残す（「ゲート 1 OK」など）。PR の承認（Approve）は使わない。** 承認は後から積んだテストと実装にも残って見え、コードを読まずに承認したのと区別できなくなるため。
- **計画とテストの照合は、ドラフトでない PR で CI が必ず流す。** ドラフトの間は、テストがまだ無いので流さない。手元でも `mise run pr` がドラフトでないときだけ流す。
- ゲート 1 の後に計画を直したら、直したことを PR のコメントで伝える。

## 結果（この判断で受け入れること）

- PR がドラフトのまま数日開くことがある。「ブランチは 1 日以内にマージ」の目安は、ドラフトを外してからの時間として読む。
- ドラフトの間は CI の照合が流れないので、計画とテストのずれはドラフトを外したときに初めて機械で分かる。
- ゲート 1 を通ったかはコメントで見るので、機械では確かめていない。ドラフトを外す前にコメントがあるかは、最終のレビューで見る。
- GitHub の設定で、新しいコミットが積まれたら古い承認を取り消す（dismiss stale approvals）ようにしておくと、承認を誤って使ったときの害が小さくなる。この設定はまだ入れていない。

## この ADR で決めないこと

- 誰がゲート 1 のレビュアーになるか（人数、順番）。チームで運用しながら決める。
- 計画の質問に答える責任は、計画を始めた人が持つ。その場で答えられないことは、本人が関係者に聞いて決める。質問を役割ごとに振り分ける仕組みは作らない。

## 確かめ方

- 計画とテストの照合は CI（ドラフトでない PR）で `mise run plan:verify-changed` が流れる。
- ゲート 1 の記録（コメント）は、最終のレビューで人が見る。

## 見直しの条件

- ドラフトの承認を実装の承認と取り違えたことが実際に起きた → dismiss stale approvals を必須にする、またはゲート 1 の記録を機械で確かめる
- ドラフトの期間が長く、他の PR とのコンフリクトが増えた → 計画の PR を B のように分けることを検討する
- Azure DevOps に移った → ドラフトの PR と Build validation の組み合わせで、同じ切り替えができるかを確かめる
