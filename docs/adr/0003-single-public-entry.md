# ADR-0003: 入口を Front Door 1 つにし、フロントとバックを 1 つのコンテナ・1 つの App Service にまとめる

- 状態: 採用（2026-11-14）
- 関連: [ADR-0002](0002-hosting-app-service.md)、[infra/docs/azure-infra-guardrails.md](../../infra/docs/azure-infra-guardrails.md)（G1）、[ワークロードの定義（Front Door のオリジンと待ち受けポート）](../../infra/workload/main.bicep)、[Policy の定義](../../infra/bootstrap/modules/policy.bicep)

## 背景（なぜ決める必要があるか）

Angular の SPA はブラウザで動くので、ブラウザから API に届く経路が必要になる。

このプロジェクトでは AI がアプリやデプロイ定義を追加していく。
「外部から届く口」や「動いているアプリ」が増えるほど、どれが意図したものかをレビューで見分けにくくなる。
そこで、**外部から届く口を 1 つに固定し、アプリ自体には Azure Policy で直接届かないようにしたい**。

## 選択肢

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A. 1 コンテナ・1 App Service（採用）** | Angular のビルド成果物と Python の API を 1 つのイメージにまとめる。Front Door は全パスをこのアプリに送り、`/api` はアプリ内でルーティングする | アプリ・イメージ・ID・Front Door の経路がそれぞれ 1 つで、レビューする場所が最も少ない。最初から同一オリジンなので CORS も振り分け設定も不要 | フロントだけの変更でもイメージ全体を作り直す。フロントとバックを別々にスケールできない。静的ファイルの配信を Python（または同居の nginx）が担う |
| B. 2 アプリを Front Door で振り分け | web と api を別の App Service にし、Front Door が `/api/*` を api に送る | フロントとバックを別々にデプロイ・スケールできる | アプリ・ID・経路が 2 つずつになる。Front Door のルート優先順位という設定に依存する |
| C. web が api に中継 | Front Door のオリジンは web だけ。web のサーバーが api に転送する | Front Door の経路は 1 つ | web に中継用のサーバーコードが必要。アプリは 2 つのまま |
| D. api を独立して公開 | ブラウザが api の URL を直接呼ぶ | 構成が単純 | 外部の口が 2 つ。CORS の設定が必要 |

## 決定

**A を採用する。**

- アプリへのパブリックアクセスを無効にし、Azure Policy の Deny で強制する。
  AI が新しいアプリを追加して公開しようとしても、デプロイが失敗する。
- 外部から届く経路は、Front Door のオリジンとしてインフラの定義の 1 か所に列挙したものだけにする。
  経路を増やすにはその一覧を変える必要があり、差分としてレビューで必ず見える。

アプリ側への影響（インフラが前提にすること）:

- イメージは 1 つ、待ち受けポートは 1 つ。ポートはインフラの引数として渡す。
- API は `/api` 配下に置き、それ以外のパスは Angular の静的ファイルを返す（未知のパスは `index.html`）。
- Angular は API を相対パス（`/api/...`）で呼ぶ。API の URL を設定に持たない。
- 認証・認可は API で必ず行う（Front Door を通ることは認証の代わりにならない）。

## 結果（この判断で受け入れること）

- **フロントだけの変更でも、毎回まとめてデプロイする。** 無駄は出るが、このテンプレートの規模では、デプロイ単位が 1 つである単純さ（バージョンのずれが起きない、ロールバックも 1 つ）の方が効く。ビルドはマルチステージの Dockerfile とキャッシュで短くできる。
- **静的ファイルをアプリが返すのは、性能的に不利。** Front Door のキャッシュを静的ファイルに効かせれば、アプリまで届く静的リクエストは少なくなる。必要になったら Front Door のルールで足す。
- **1 つの ID が Key Vault の読み取り権限を持つ。** フロントのコード（ブラウザで動く JavaScript）はサーバー側の ID を使えない。サーバー側で動くのは API だけなので、実質の権限は 2 アプリに分けた場合と変わらない。

## この ADR で決めないこと

- **静的ファイルを Python が返すか、同じコンテナ内に nginx を同居させるか。** アプリの骨格を作るときに決める。

## 確かめ方

- アプリへのパブリックアクセスは、Azure Policy の Deny でデプロイ時に止める。
- Front Door のオリジンの一覧が変わる差分は、レビューでセキュリティ境界の変更として見る（[レビューの観点](../review-guide.md)）。

## 見直しの条件

- フロントとバックを別のチームが別の頻度でリリースするようになった → B を再検討
- 静的ファイルの配信負荷がアプリの性能に影響するようになった → Front Door のキャッシュ、または静的ファイルを Storage に分ける
- 認証方式の決定で、ブラウザにトークンを置かない要件が出た → BFF としての役割をこのアプリに持たせる
