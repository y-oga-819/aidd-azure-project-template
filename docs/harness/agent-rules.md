# AI エージェントへの約束

AI のエージェント(Claude Code など)が、このハーネスで作業するときに守ること。
`CLAUDE.md` から読み込まれ、毎回のセッションで読まれる。短く保つため、理由は 1 行だけにし、詳しい手順はリンク先に置く。人に向けた説明は README とリンク先の文書に書く。

## 進め方

- **振る舞い(テストで確かめる仕様)を足す・変える作業は、`/planning` で計画を作ってから始める。** 人間のゲート 1(計画だけのドラフト PR に、レビュアーが「ゲート 1 OK」などとコメントする)を通るまで、テストも実装も書かない。コードを書く前が、誤りを直すのに一番安いため。計画を省くかは人間が決める。
- **ゲート 1 の後は、テストを先に書き、失敗することを確かめてから実装する。** テストが計画のテストケース一覧どおりかは `mise run plan:verify <計画>` で照合する。
- **仕様の正本はテスト。** テストを通すために、既存のテストの期待値・テスト名・テスト ID を変えたり、テストを消したりしない。変える必要があると分かったら、止まって人間に伝え、計画の表に「変更」「削除」の行として書く。
- テストの書き方(日本語のテスト名、ID、docstring の why)は [テスト戦略](../testing-strategy.md) の「書き方の規約」に従う。次の ID は `mise run test:next-id <接頭辞>` で出す。
- 業務ルールはバックエンドのドメイン(`backend/src/app/domain/`)に置き、フロントエンドに置かない。
- 流れの全体と、コンフリクトが起きたときの解消は [開発の進め方](../development-flow.md) にある。

## コマンド

- **コマンドは mise のタスクを使う**(`mise tasks --all` で一覧)。`pytest` や `ruff` を直接叩かない。人も CI も同じ入口を使い、結果を揃えるため。
- **push の前と、作業が終わったと伝える前に `mise run check` を流し、通す。**
- 検査を通すために、検査を外さない(`# noqa`、`# type: ignore`、`pytest.skip`、設定で除外する、など)。必要だと考えたら、理由を添えて人間に聞く。
- push は `mise run push`、PR は `mise run pr` で作る(計画だけのゲート 1 は `mise run pr --draft`)。`gh` や `az repos` を直接使わない。GitHub と Azure DevOps を切り替えられるようにしているため。

## PR

- 本文は [PR テンプレート](../pull_request_template.md) の形で書く。該当しない欄は消さずに「なし」と書く。
- 【AI の手動確認】には、実際にやって結果を見たことだけを書く。確かめていないことは「確かめられていないこと」に書く。
- 人間が判断すべき変更(公開インターフェース、セキュリティ境界、元に戻しにくい変更、依存の追加・更新)は、AI だけで決めない。PR の該当欄にチェックを付け、判断してほしいことを書く。
- PR より長く効く判断をしたら、ADR の下書きを提案する([ADR の運用ルール](../adr/README.md))。

## 前提

- このプロジェクトに固有のこと(何を作るか、想定する構成と違う点)は [プロジェクトの前提](../project-context.md) にある。この文書と食い違ったら、プロジェクトの前提に従う。
- ハーネスのファイル(この文書、skill、`tools/`、`mise-tasks/` など)を足したり改名したりしたら、[配るファイルの一覧](files.txt) も直す。決まりは [ハーネス](README.md) の「守ること」にある。
