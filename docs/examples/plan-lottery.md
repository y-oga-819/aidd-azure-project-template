# 計画: 抽選型商品の追加

## ストーリー
> 抽選型商品を追加したい。カートに入れて申し込むと与信だけ取る。抽選で当選したら通常どおり発送して注文完了、落選したら与信を解放する。

## 現在の仕様（`mise run docs:spec order/lifecycle` で既存テストから生成）
| id | 現在 | イベント | 次 |
|---|---|---|---|
| ORDER-1 | 確定 | キャンセル要求 | キャンセル済 |
| ORDER-2 | 確定 | 出荷指示 | 出荷指示済 |
| ORDER-4 | 出荷指示済 | 発送 | 発送済 |
| ORDER-7 | 発送済 | 配達 | 配達完了 |
| … | | | |

決済の現状（`docs:spec payment`）: 注文確定時に与信を取り、発送時に売上を確定する。

## 1. なぜ
人気商品で転売目的のアクセス集中が起き、サーバー負荷と購入者の不満が出ている。先着順ではなく、申込期間を設けて抽選する。

## 2. テストケースの洗い出し(網羅の根拠)

### 2-1. 複雑さの種類
| 種類 | 該当 | 理由 |
|---|---|---|
| 状態とイベント | ✅ | 新しい状態（抽選待ち・落選）が増える |
| 外部依存の失敗 | ✅ | 与信の解放・売上確定は決済代行への呼び出しで、失敗しうる |
| 時間 | ✅ | 与信には有効期限がある。抽選日が期限を過ぎると売上を確定できない |
| 条件の組み合わせ | — | |

### 2-2. 組み合わせ(状態遷移)
既存の状態6つ × イベント6つに、**状態が2つ・イベントが2つ増える**。
新しく考えるべきセルは「新しい行（2 × 8 = 16）」＋「新しい列 × 既存の行（6 × 2 = 12）」＝ **28セル**。

| 状態 \ イベント | キャンセル要求 | 出荷指示 | 発送 | 倉庫承認 | 倉庫却下 | 配達 | **当選** | **落選** |
|---|---|---|---|---|---|---|---|---|
| **抽選待ち**（新） | キャンセル済 ※1 | ✗ | ✗ | ✗ | ✗ | ✗ | 確定 | 落選 |
| **落選**（新・終端） | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| 確定 | （既存） | （既存） | | | | | ✗ ※2 | ✗ ※2 |
| 出荷指示済 | | | | | | | ✗ | ✗ |
| キャンセル申請中 | | | | | | | ✗ | ✗ |
| 発送済 | | | | | | | ✗ | ✗ |
| 配達完了 | | | | | | | ✗ | ✗ |
| キャンセル済 | | | | | | | ✗ ※3 | ✗ ※3 |

- ※1 抽選前のキャンセルは即時。与信も解放する
- ※2 通常注文に当選/落選イベントは来ない。来たら拒否する
- ※3 **抽選前にキャンセルした人が当選に選ばれた場合**。抽選の対象から外すので、来たら拒否する（下の質問で確認）
- 当選後は「確定」に合流し、以降は既存の通常フロー（出荷指示 → 発送で売上確定）に乗る

### 2-3. まとめた組み合わせとその理由
拒否するマス(✗)は、すべて 1 つのパラメータ化テスト(ORDER-0)にまとめる。答えが「拒否」で同じであり、1 ケースが一瞬で終わるため。

### 2-4. 質問と回答
| # | 質問 | なぜ聞くか | 回答 | 影響 |
|---|---|---|---|---|
| Q1 | 与信の有効期限（決済代行の契約では60日）を、抽選日が超えることはありますか？ | 外部の有効期限が業務の期間より短いと、当選しても売上を確定できない（観点: 時間） | ありうる | **販売設定で「抽選日 ≤ 申込開始日 + 55日」を強制する**（5日は余裕）。テスト追加 |
| Q2 | 当選後、発送時の売上確定に失敗したら？（カード停止など） | 外部依存は失敗する。新しい流れだけ特別扱いが要るかで、テストが増えるかが決まる（観点: 外部依存の失敗） | 既存の通常注文と同じ扱い（オペレーター対応） | 新規テストなし。既存の仕様に乗る |
| Q3 | 落選時の与信解放が失敗したら？ | 失敗を決めないと、与信が解放されないまま誰も気づかない（観点: 外部依存の失敗、失敗に気づけるか） | 3回リトライし、それでも失敗ならオペレーターに通知 | 統合テスト追加 |
| Q4 | 抽選商品と通常商品を同じカートで買えますか？ | 既存のカートと決済の流れに、与信だけの注文が混ざると壊れる（観点: 既存のルールとの絡み） | 買えない（カートを分ける） | 単体テスト追加 |
| Q5 | 1人で何口申し込めますか？ | 上限がないと、転売を防ぐという目的が果たせない（観点: 境界値） | 1商品につき1口 | 単体テスト追加 |
| Q6 | 抽選のやり直し（バッチの再実行）で、二重に当選/落選を処理しませんか？ | バッチは再実行される。二重に処理すると、二重の通知や与信の二重解放が起きる（観点: 冪等性と二重実行） | しないこと | 統合テスト追加（冪等性） |
| Q7 | 抽選結果を後から説明できる必要は？ | 乱数の結果は記録がないと再現できず、問い合わせに答えられない（観点: 記録と説明） | 問い合わせ対応のため必要 | 乱数のシードを記録し、同じシードで同じ結果になることをテスト |
| Q8 | 抽選前にキャンセルした人は抽選対象から外れますか？ | 状態遷移表の空欄（キャンセル済 × 当選）。拒否か考え忘れかを決める（観点: 状態の追加） | 外れる | 単体テスト（抽選の入力から除外） |

## 3. 判断と捨てた案

### ADR に残す判断

#### 1. 与信をいつ取るか

今後の「予約商品」にも効くので、ADR に残す。PR 概要にはその ADR へのリンクと 1 行要約だけを書く。

##### 採用
- **申込時に与信を取る。** 当選者は必ず支払える状態にしておける。期限切れは、販売設定の制約（Q1）で防ぐ。

##### 不採用
- 当選時に与信を取る: 当選後に与信が通らない人が出る。その分、繰り上げ当選の仕組みが要り、複雑になる。

### この PR だけの判断（ADR に残さない）

#### 2. 抽選の乱数のシードをどこに記録するか（Q7）

##### 採用
- **抽選の実行記録（抽選回ごとの行）にシードを保存する。** 問い合わせのたびに、同じシードで抽選を再現できる。

##### 不採用
- アプリのログに出す: ログの保持期間を過ぎると再現できなくなる。
- シードを記録せず、当選者の一覧だけを残す: 「なぜこの人が当選したか」を説明できない。
