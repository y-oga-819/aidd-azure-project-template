# PR レビューの観点

AI がコードの大半を書く前提で、人間のレビュアーが何を確かめるかをまとめる。
PR の作成者が書く内容は [pull_request_template.md](pull_request_template.md) にある。

## 考え方

- **人間が守るのは「なぜ」「どう動けば正しいか」「公開インターフェース」「セキュリティ境界」。**
  コードの書き方の細部は、AI と CI(`mise run check`)に任せる。
- **全行を読まない。** PR 概要から「どこを読むべきか」を決め、そこを深く読む。
- **概要は AI が書いている。** もっともらしい文章を信じず、テスト名・ファイル・リンク先で裏を取る。

## 確かめる順番

### 1. なぜ

- 解決する困りごとが書かれていて、それが本当に解きたいことか。
- 変更の範囲が、その目的に対して広すぎないか(ついでの変更が混ざっていないか)。

### 2. 受け入れ条件と確かめる手段

PR の正しさを判断する中心。ここに最も時間を使う。

- 条件は「どう動けば正しいか」を言えているか。実装の説明になっていないか。
- 足りない条件はないか。特に、失敗時・権限がないとき・境界値の振る舞い。
- 確かめる手段(テスト名など)は、その条件を本当に確かめているか。
  テスト名だけで怪しければ、そのテストの中身だけ読む。
- **「なし」と書かれた行**は、自動で守られていない約束。妥当か、手段を足すべきかを判断する。

### 3. 人間が判断すべき変更

チェックが付いた項目は、該当するファイルを読む。

| 項目 | 見ること |
|---|---|
| 公開インターフェース | 利用者(他チーム、画面、AI 向けの指示)への影響。後から変えにくい名前や形になっていないか |
| セキュリティ境界 | 外部から届く口が増えていないか。権限が必要以上に広くないか。シークレットがコードや設定に入っていないか |
| 元に戻しにくい変更 | 失敗したときの戻し方が決まっているか |
| 依存の追加・更新 | 本当に必要か。保守されているか。ライセンス |

**チェックが付いていなくても、diff の場所で疑う。** AI が「該当なし」を誤って書くことがある。
例えば、次のファイルが変わっていれば該当する可能性が高い。

- `infra/`、`*.bicep`、`.github/workflows/`、`azure-pipelines.yml` → セキュリティ境界
- API のルーティング、スキーマ、`mise.toml` のタスク名 → 公開インターフェース
- `pyproject.toml`、`package.json`、ロックファイル → 依存

### 4. 判断と捨てた案

- 捨てた案の理由に納得できるか。前提が変われば逆転する判断なら、その前提が書かれているか。
- 次の PR にも効く判断なのに ADR になっていなければ、ADR を求める。

### 5. 確かめられていないこと

- マージしてよい未検証か、マージ前に確かめるべきかを判断する。
- 「確かめられていないこと」が空の大きな PR は、書き漏れを疑う。

## 読まなくてよいもの

- 整形、命名、型、テストが通るか → CI が見る
- 図解 → 理解の補助。正しさの根拠にはしない
