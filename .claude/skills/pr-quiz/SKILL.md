# PR 前の理解度テスト

PR 概要の下書きができた後、`mise run pr` の前に呼ぶ。作成者(人間)が PR を説明できるかを確かめ、全問正解したら PR を作る。
任意の skill で、使わずに `mise run pr` を直接呼んでもよい。

## この skill の狙い

- **AI が書いた PR を、作成者が説明できない状態でレビューに出さない。** PR 概要は AI が下書きしている([PR テンプレート](../../../docs/pull_request_template.md))。作成者が中身を理解していないと、レビュアーの質問に答えられず、「なぜ」と「受け入れ条件」を人間が守るという前提([レビューの観点](../../../docs/review-guide.md))が崩れる。
- **出題は人間が守る欄から出す。** なぜ、受け入れ条件と確かめる手段、人間が判断すべき変更、判断と捨てた案、確かめられていないこと。コードの書き方の細部は CI と AI に任せている部分なので出さない。
- **覚えているかではなく、使えるかを問う。** 本文の言い回しを覚えていれば解ける問題は、本文を読み直せば誰でも通る。「この案を選んでいたら何が困るか」「この前提が崩れたら何が起きるか」のように、本文に答えがそのまま書かれていない問いにする。
- **不正解は学ぶ機会にする。** 不正解のたびに、正解と理由と、本文やコードのどこを読めば分かるかを返す。
- **食い違いは、本文の誤りの合図でもある。** 作成者の答えが本文と違うとき、間違っているのは AI が書いた本文の方かもしれない。決めつけず、作成者に確かめる。

## 読むもの

| 材料 | 取り方 | 使い方 |
|---|---|---|
| PR 概要の下書き | 作成者に場所を聞く。無ければ先にテンプレートで下書きする(下の「本文ファイル」) | 出題の中心 |
| 差分 | `git diff "$AIDD_BASE_BRANCH"...HEAD`、`git log "$AIDD_BASE_BRANCH"..HEAD` | 本文が差分と合っているか確かめる。応用の問いの材料 |
| 計画 | `docs/plans/` にあり、本文からリンクされていれば読む | なぜ、質問と回答、テストケース一覧 |
| テスト | 差分に含まれるテスト。受け入れ条件の【自動検査】に書かれたテスト | 「どのテストが落ちるか」の問いの材料 |
| ADR | 本文からリンクされたもの | 判断の問いの材料 |

`AIDD_BASE_BRANCH` が無ければ `main` を使う。

## 進め方

### 1. 材料を集め、本文と差分を突き合わせる

上の材料を読む。出題の前に、本文が差分と合っているかを見る。合っていなければ出題せず、先に本文を直すよう作成者に伝える。誤った本文から出題すると、正しく理解している作成者を不正解にしてしまうため。

- 差分にある変更が本文のどこにも書かれていない(特に [review-guide.md](../../../docs/review-guide.md) の「チェックが付いていなくても、diff の場所で疑う」に当たるファイル)
- 本文の【自動検査】に書かれたテストが差分にも既存のテストにも無い
- テンプレートの欄が空のまま(「なし」とも書かれていない)

### 2. 問題を作る

[question-patterns.md](question-patterns.md) の型から選ぶ。

- **3 択を 3〜4 問と、なぜの記述を 1 問。** 小さな PR(1 ファイルの修正など)は 3 択 2 問と記述 1 問でよい。問題を増やしても理解は深まらず、作成者が面倒になって読まずに答えるようになる。
- **欄の配分。** 受け入れ条件から必ず 1 問以上出す(PR の正しさの中心なので)。残りは、判断と捨てた案、確かめられていないこと、人間が判断すべき変更のうち、この PR で中身が濃い欄から出す。「なし」の欄からは出さない。
- **選択肢は、ありがちな誤解にする。** 明らかに違う選択肢は当て推量の確率を上げるだけになる。捨てた案、本文の別の行、似ているが違うテスト、のように、読み飛ばしていると選びそうなものにする。
- **正解の位置は問題ごとに変える。** 毎回同じ位置だと位置で当てられる。
- **答えは作成者に見せない。** 出題前に、作成者に見えない形で(自分の中だけで)正解と理由を決めておく。

### 3. 出題する

- 3 択は AskUserQuestion ツールがあれば使い、まとめて出す(1 回で最大 4 問)。選択肢の説明欄に正解の手がかりを書かない。無ければ番号付きの選択肢で出し、番号で答えてもらう。
- 記述は 3 択の回答を受け取った後に、普通のメッセージで出す。「1〜2 文で、自分の言葉で」と添える。
- 出題の前に一度だけ「本文やコードを見ずに答えてください。見ないと答えられないなら、それがレビュー前に読み直す場所です」と伝える。見ているかどうかは確かめない。正直さに任せる。

### 4. 採点して解説する

3 択:

- 正解でも不正解でも、1〜2 行で理由を返す。正解した人にも、どこを読めば確かめられるか(本文の欄、ファイル、テスト名)を返す。
- 不正解なら、正解と理由と、本文やコードのどこに書かれているかを返す。作成者が「本文の方が違う」と言ったら、差分を見て確かめる。本文が誤っていれば、その問題は採点から外し、本文を直す箇所を示す。

記述(なぜ):

- 採点の基準は、本文の「なぜ」の要点(誰の、どんな困りごとを解決するか)が入っているか。言い回しや長さは問わない。
- 要点を「誰の」「どんな困りごと」「この PR でどう良くなるか」に分け、どれが入っていてどれが足りないかを返す。足りなければ不正解にする。
- 作成者の説明の方が本文より的確なら、そう伝え、本文の「なぜ」を作成者の言葉で書き直すことを提案する。

### 5. 不正解だった観点を出し直す

- 不正解だった問題ごとに、**同じ観点を別の問いで** 出し直す。同じ問題を出し直すと、消去法で 2 回目に当たってしまう。
- 同じ観点で 2 回続けて不正解なら、出し直しをやめる。その観点について本文とコードのどこを読めばよいかを示し、「読み直してから、もう一度この skill を呼んでください」と伝えて終える。PR は作らない。

### 6. 全問正解したら PR を作る

1. 結果を短く伝える。出し直しで正解した観点があれば、それを並べる(レビューで聞かれやすい場所なので)。
2. `mise run pr -b <本文ファイル>` を流す。タイトルなど `mise run pr` に渡す引数は、作成者が最初に指定したものを使う。作成者が「PR は作らなくていい」と言っていたら流さない。
3. `mise run pr` が失敗したら(check の失敗、コミットされていない変更など)、そのエラーをそのまま伝える。理解度テストはやり直さなくてよい。

## 本文ファイル

- `mise run pr` は作業ツリーに未コミットのファイルがあると止まる。本文ファイルはリポジトリの外(例: `${TMPDIR:-/tmp}/pr-body-<ブランチ名>.md`)に置く。
- 作成者が本文を用意していなければ、[テンプレート](../../../docs/pull_request_template.md)の形で下書きし、作成者に「なぜ」と「受け入れ条件」を確かめてもらってから出題する。下書きの直後に出題すると、AI が書いたばかりの文章を AI が問うだけになる。

## やらないこと

- コードの書き方の細部(変数名、ライブラリの使い方、整形)を出題しない。CI と AI に任せている部分なので。
- 本文の文章をそのまま問題文や選択肢に写さない。言い回しを覚えているかを問うことになる。
- 不正解の結果を PR 本文やコミットに書かない。理解度テストは作成者の準備のためで、評価のためではない。記録すると、点を取るための作業になる。
- 全問正解していないのに PR を作らない。作成者が PR を出したいなら、この skill を使わずに `mise run pr` を直接呼べることを伝える。
