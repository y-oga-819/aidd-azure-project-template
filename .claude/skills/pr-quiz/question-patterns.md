# 出題の型

PR テンプレートの欄ごとに、何を確かめたいかと問いの型を並べる。
例は [計画の例(抽選型商品)](../../../docs/examples/plan-lottery.md) の PR C(抽選バッチと与信の解放)を想定している。

どの型も、**本文の文をそのまま問うのではなく、本文の内容を使って考えさせる** ことを狙う。
本文を覚えているかを問う型(「この PR の受け入れ条件はどれか」)は使わない。本文を読み直せば誰でも通るため。

## なぜ(背景と目的)

確かめたいこと: 誰のどんな困りごとを解くための変更かを、本文を見ずに言えるか。レビュアーに「これ要る?」と聞かれて答えられるか。

### 記述: 自分の言葉で説明する(毎回 1 問)

> この PR がなぜ必要かを、PR を読んでいない同僚に 1〜2 文で説明してください。

- 採点の要点: 誰の / どんな困りごと / この PR でどう良くなるか。
- 例の要点: 人気商品で転売目的のアクセスが集中している(誰の困りごと: 購入者とサーバー)/ 抽選にするために、落選者の与信を解放するバッチが要る(この PR の役割)。
- 「抽選バッチを作るため」のように、何をするかだけで困りごとが無い答えは不正解にする。

### 3 択: 範囲の外を見分ける

> 次のうち、この PR の目的の **外** にあるものはどれですか?

- 確かめたいこと: ついでの変更や、次の PR でやることとの線引きが分かっているか。
- 選択肢: 計画の PR の分割で別の PR にしたもの、「増えなかったもの」、この PR の目的そのもの。
- 例: (1) 落選者の与信を解放する (2) 抽選の申込画面を作る ← 正解(PR D) (3) 抽選を再実行しても二重に処理しない

## 受け入れ条件と確かめる手段

確かめたいこと: 何が守られていれば正しいかと、それを何が守っているか(テストか、人の確認か)を分かっているか。PR の正しさの中心なので、毎回 1 問以上出す。

### 3 択: どのテストが落ちるか

> 抽選バッチが、2 回目の実行でも落選者に通知メールを送るように変わってしまったとします。どのテストが落ちますか?

- 確かめたいこと: 受け入れ条件とテストの対応が頭に入っているか。
- 選択肢: 正しいテスト、名前の似た別のテスト、「どのテストも落ちない」。
- 例: (1) LOTTERY-11 最長のハッピーパス (2) LOTTERY-13 2 回実行しても 1 回しか行われない ← 正解 (3) どのテストも落ちない
- 「どのテストも落ちない」が正解になる問いも作ってよい。【自動検査】が「なし」の行を問うときに使う。

### 3 択: 自動で守られていない約束

> 次の約束のうち、CI では確かめられておらず、レビュアーか作成者が手で確かめているものはどれですか?

- 確かめたいこと: 【自動検査】が「なし」の行(自動で守られていない約束)を作成者が把握しているか。レビュアーが最も注意して見る行なので、作成者が知らないと危ない。
- 選択肢: 【自動検査】が「なし」の行 1 つと、テストで守られている行 2 つ。「なし」の行が無い PR では出さない。

### 3 択: 失敗したとき

> 与信の解放が決済代行側で失敗し続けたとき、注文はどうなりますか?

- 確かめたいこと: 異常系の振る舞いを作成者が言えるか。レビュアーが最初に聞くことが多い。
- 選択肢: 正しい振る舞い、捨てた振る舞い、何もしない(エラーを握りつぶす)。
- 例: (1) 3 回やり直した後オペレーターに通知し、落選・解放待ちで残る ← 正解(LOTTERY-12) (2) 解放できるまでやり直し続ける (3) 落選にして処理を終える

## 人間が判断すべき変更

確かめたいこと: 公開インターフェース、セキュリティ境界、元に戻しにくい変更、依存の追加を、作成者が自分で把握しているか。チェックが付いている欄からだけ出す。

### 3 択: 戻し方

> この PR のマイグレーションを本番に流した後に問題が見つかったら、どう戻しますか?

- 確かめたいこと: 元に戻しにくい変更の戻し方を作成者が言えるか。言えなければ、本文に戻し方が書かれていないことが多い。
- 選択肢: 本文に書かれた戻し方、戻せない前提の選択肢(「戻せないので前に進めて直す」)、よくある誤解(「PR を revert すれば戻る」)。

### 3 択: 権限と届く範囲

> この変更で、新しくインターネットから届くようになったものはどれですか?

- 確かめたいこと: セキュリティ境界の変化を作成者が把握しているか。インフラのコードや CI の定義を変えた PR で出す(このプロジェクトでの場所は [プロジェクトの前提](../../../docs/project-context.md) の「レビューで疑う場所」)。
- 選択肢: 実際に増えた口、増えていない(閉域のまま)口、「何も増えていない」。

## 判断と捨てた案

確かめたいこと: 選んだ理由と、どんな前提が変われば判断が逆転するかを分かっているか。レビュアーに「なぜ B にしなかったの?」と聞かれて答えられるか。

### 3 択: 捨てた案を選んでいたら

> 抽選のシードを、抽選の実行記録ではなくアプリのログに出していたら、何が困りますか?

- 確かめたいこと: 捨てた理由を、本文の言い回しではなく結果として言えるか。
- 選択肢: 本文の不採用の理由、別の捨てた案の理由、もっともらしいが本文に無い理由。
- 例: (1) ログの保持期間を過ぎると抽選を再現できない ← 正解 (2) なぜこの人が当選したかを説明できない(シードを記録しない案の理由) (3) ログが大きくなりすぎる

### 3 択: 逆転する前提

> 次のどれが起きたら、「申込時に与信を取る」という判断を見直すべきですか?

- 確かめたいこと: 判断の前提を作成者が分かっているか。ADR に残した判断で出すとよい。
- 選択肢: 前提が崩れる変化(例: 抽選日が与信の有効期限を超える販売が必要になった)、判断に関係しない変化 2 つ。

## 確かめられていないこと

確かめたいこと: 何を確かめずにマージしようとしているかと、それが外れたら何が起きるかを分かっているか。

### 3 択: 前提が外れたら

> 「決済代行のサンドボックスでは、与信の解放 API を実際には呼んでいない」とあります。この前提が外れていたら、本番で最初に何が起きますか?

- 確かめたいこと: 未検証の前提を、作成者がマージしてよいと判断できる程度に理解しているか。
- 選択肢: 実際に起きること、起きないこと(テストで守られていること)、大げさな結果。
- 「確かめられていないこと」が「なし」の PR では出さない。ただし、差分の大きさに比べて「なし」が不自然なら、出題の前に書き漏れを疑って作成者に聞く([review-guide.md](../../../docs/review-guide.md) の 5)。

## 選択肢の作り方の注意

- 3 つの選択肢は長さと書きぶりを揃える。正解だけが長く丁寧だと、それで当たる。
- 「すべて正しい」「どれでもない」は使わない。理解を問わずに消去法で解けるため。例外は「どのテストも落ちない」で、これは自動で守られていない約束を問うために使う。
- 引っかけ(否定の否定、細かい数字の違い)にしない。引っかけで不正解になっても、理解が足りないことにはならない。
