# 悪手の観点

プランニング skill が計画を点検するときの観点。**気づくきっかけがある観点だけ** を質問にする。
質問の「なぜ聞くか」には、各観点の「見落とすと何が起きるか」を、そのストーリーに合わせて具体的に書く。

観点を足すときは、実際に見落とした例(どのストーリーで、何が起きたか)と一緒に足す。使われない観点は削る。

## 既存のルールとの絡み

- 気づくきっかけ: 既存の機能に条件や対象を足す。「〜の場合も」「〜と同じように」という言い方。
- 見落とすと: 新しいルールと既存のルールが同時に当てはまる入力で、どちらが勝つか決まっていない。実装した人の順番で勝手に決まる。
- 質問の例: 「既存の SHIPPING-3(ゴールド会員は無料)と、今回の離島の追加料金が同時に当てはまるとき、どちらが優先ですか」
- 調べ方: `mise run docs:spec <機能名>` で既存のテストを並べ、新しい条件と重なるものを探す。重なりは名前の付いたテストにする(テスト戦略 4 章の 6)。

## 境界値

- 気づくきっかけ: 数値、日時、件数、文字数の閾値。「以上」「超える」「まで」「以内」。
- 見落とすと: 「以上」と「超える」の取り違えが、境界ちょうどの 1 件でだけ表に出る。テストが境界の両側を持っていないと気づけない。
- 質問の例: 「5,000 円ちょうどは無料ですか、有料ですか」「0 件、1 件、上限ちょうど、上限 + 1 のときはそれぞれどうなりますか」
- テスト: 境界の両側を 1 ケースずつ。境界は同じパラメータ化テストの中に足す。

## 異常系

- 気づくきっかけ: 利用者や他システムからの入力がある。処理が複数の段階を持つ。
- 見落とすと: 正常系だけの計画になり、不正な入力や途中の失敗で何が起きるかを実装者が勝手に決める。エラーの見せ方(メッセージ、ステータスコード)が画面ごとにばらばらになる。
- 質問の例: 「必須の項目が空のとき、利用者には何を返しますか」「3 段階のうち 2 段階目で失敗したら、1 段階目の結果は取り消しますか、残しますか」
- テスト: 入力の検証はドメインの単体。途中の失敗と取り消しは統合。

## 状態の追加

- 気づくきっかけ: 「〜待ち」「〜中」「〜済み」という言葉が増える。今の状態によって同じ操作の結果が変わる。
- 見落とすと: 新しい状態で既存の操作(キャンセルなど)が来たときと、既存の状態に新しいイベントが来たときの振る舞いが決まっていない。終端の状態から抜け出せてしまう。
- 質問の例: 「抽選待ちの注文はキャンセルできますか」「通常の注文に『当選』のイベントが来たら拒否してよいですか」
- 洗い出し: 状態 × イベントの全マスを書き、新しい行と新しい列のマスを数える(計画の例 plan-lottery.md の 2-2)。空欄は「拒否」か「考え忘れ」かを確かめる。

## 計算の順序と端数

- 気づくきっかけ: 割引、税、送料、ポイント、按分など、計算を複数かける。
- 見落とすと: 順序を入れ替えると 1 円ずれる。端数を何回、どこで丸めるかが実装によって変わる。
- 質問の例: 「クーポンは税込みの金額から引きますか、税抜きから引きますか」「端数は明細ごとに丸めますか、合計で 1 回丸めますか」
- テスト: 各計算は独立した関数で網羅し、合成の正しさは代表的な計算例 2〜3 個で確かめる(テスト戦略 4 章の 7)。

## 時間

- 気づくきっかけ: 期限、期間、締切、改定日、「毎日」「月末」。外部サービスの有効期限(与信、トークン、署名付き URL)。
- 見落とすと: 期限ちょうどの扱い、タイムゾーン(サーバーは UTC、利用者は日本時間)、月末や閏年でずれる。外部の有効期限が業務の期間より短いと、後で処理できなくなる。
- 質問の例: 「締切の 23:59:59 と 00:00:00 はどちらが締切後ですか。どのタイムゾーンで判定しますか」「抽選日が与信の有効期限(60 日)を超えることはありますか」
- テスト: 時刻は引数で渡し、境界の日時を固定してテストする(テスト戦略 5 章)。

## 外部依存の失敗

- 気づくきっかけ: 決済、メール、外部 API、ストレージ、別チームのサービスを呼ぶ。
- 見落とすと: タイムアウトを「失敗」と扱ったが、実は相手側では成功していた(二重決済)。失敗をログに出すだけで、誰も気づかない。
- 失敗の種類ごとに決める: タイムアウト(相手で成功したか分からない) / 拒否(相手が明確に断った) / 一部だけ成功 / 遅れて結果が届く
- 質問の例: 「決済代行がタイムアウトしたら、注文は確定扱いにしますか、保留にしますか。保留ならいつ、誰が確かめますか」「やり直すなら何回まで、失敗し続けたら誰に知らせますか」
- テスト: 統合テストで、管理外の依存だけをモックにし、失敗の種類ごとに 1 本(テスト戦略 3 章)。

## 冪等性と二重実行

- 気づくきっかけ: バッチ、再実行、やり直し、Webhook の受信、利用者のボタンの連打、キューからの受信。
- 見落とすと: 同じ処理が 2 回走り、二重の請求、二重の通知、在庫の二重引き当てが起きる。
- 質問の例: 「バッチが途中で落ちて再実行したとき、処理済みの分はもう一度処理されませんか」「同じ Webhook が 2 回届いたらどうしますか」
- テスト: 統合テストで、同じ入力を 2 回流して副作用が 1 回であることを確かめる。

## 同時実行

- 気づくきっかけ: 在庫、残高、枠、連番など、複数の利用者が同じものを更新する。
- 見落とすと: 最後の 1 個を 2 人が同時に買える。読み込んでから書き込むまでの間に他の更新が入る。
- 質問の例: 「最後の 1 枠に 2 人が同時に申し込んだら、どちらが取りますか。取れなかった人には何を返しますか」
- テスト: DB の制約やロックに頼るなら、本物の DB を使う統合テストで確かめる。

## 権限

- 気づくきっかけ: 操作する人の種類(会員、管理者、オペレーター、他の会社)がある。ID を URL やリクエストで受け取る。
- 見落とすと: 他人の注文を ID を変えるだけで見られる。画面でボタンを隠しただけで、API は誰でも呼べる。
- 質問の例: 「この操作ができるのは誰ですか。できない人が API を直接呼んだら何を返しますか(403 か 404 か)」「管理者は他の会社のデータも見られますか」
- テスト: 判定はバックエンドのドメインで単体テストする。画面で隠すことは認可の代わりにならない。API での拒否は統合テストで確かめる。

## セキュリティ境界

- 気づくきっかけ: 外部から届く口(API、Webhook、ファイルのアップロード)が増える。認証・認可、シークレット、ネットワーク、ID とロール、Azure Policy に触れる。利用者の入力をクエリやコマンドやパスに使う。
- 見落とすと: 認証の要らない口が意図せず増える。シークレットが設定ファイルやログに入る。権限が必要以上に広い。
- このリポジトリの前提: 外部から届く口は Front Door だけで、アプリへの直接のアクセスは Policy で拒否する([ADR-0003](../../../docs/adr/0003-single-public-entry.md))。Front Door を通ることは認証の代わりにならない。シークレットは Key Vault に置き、コードや設定に書かない([infra/docs/azure-infra-guardrails.md](../../../infra/docs/azure-infra-guardrails.md))。
- 質問の例: 「この API は認証なしで呼べてよいですか。よいなら、なぜですか」「ログにメールアドレスやカード番号の一部が出ませんか」
- 計画への書き方: PR 概要の「人間が判断すべき変更」のセキュリティ境界に当たることを、計画の判断の節に書いておく。

## 既存の契約の破壊

- 気づくきっかけ: API のパスや応答の形、画面の振る舞い、mise のタスク名、設定項目、環境変数、DB のスキーマを変える。
- 見落とすと: 古い画面や他チームのクライアント、CI、AI 向けの手順が黙って壊れる。デプロイの途中は古い版と新しい版が同時に動く。
- 質問の例: 「この応答の項目名を変えると、今の画面と他の利用者は壊れませんか。古い名前をしばらく残しますか」「デプロイの途中で古い画面から新しい API を呼んでも動きますか」
- テスト: 既存のテストが「変更」「削除」になる行を一覧に書く。削除したテストは、なぜ消してよいかを計画に書く。

## データ移行

- 気づくきっかけ: DB のスキーマや値の意味を変える。新しい必須の項目を足す。保存の形式を変える。
- 見落とすと: 既存のデータが新しい制約を満たさず、マイグレーションが本番で失敗する。戻せない変更を入れてしまう。
- 質問の例: 「既存の行には、新しい項目に何を入れますか」「マイグレーションが失敗したら、どう戻しますか。戻すときにデータは失われますか」
- 計画への書き方: 元に戻しにくい変更なので、PR の分割で最初に小さく出す。戻し方を判断の節に書く。

## 構成・基盤

ドメインのルールが無い変更(アプリの骨格、ルーティング、ビルド、デプロイ、設定)で使う。

- 気づくきっかけ: Dockerfile、ポート、パスの振り分け、ヘルスチェック、環境変数、ビルドの手順、静的ファイルの配信。
- 見落とすと: 手元では動くがコンテナの中や Azure では動かない。設定の既定値が本番に向いていない。
- このリポジトリの前提([ADR-0002](../../../docs/adr/0002-hosting-app-service.md)、[ADR-0003](../../../docs/adr/0003-single-public-entry.md)): イメージは 1 つ、待ち受けのポートは 1 つ(既定 80)。API は `/api` の下、それ以外は Angular の静的ファイルを返し、未知のパスは `index.html` を返す。Angular は API を相対パスで呼ぶ。
- 質問の例:
  - 「`/api` の下の存在しないパスには、`index.html` ではなく API の 404 を返しますか」(未知のパスを全部 `index.html` にすると、API の呼び間違いが 200 の HTML として返り、画面側で原因が分かりにくくなる)
  - 「ヘルスチェックは何を確かめますか。DB に届くことまで含めますか」(含めると DB の障害でアプリが再起動を繰り返す。含めないと、DB に届かないアプリに通信が流れる)
  - 「手元、CI、Azure で値が変わる設定はどれですか。シークレットはどこから読みますか」
- テスト: ルーティングとヘルスチェックは統合テスト(アプリを起動して HTTP で叩く)。イメージが起動して応答することは、CI でコンテナを動かして確かめるか、確かめられていないこととして PR に書く。

## 失敗に気づけるか

- 気づくきっかけ: バッチ、非同期の処理、外部依存の失敗をやり直す処理。
- 見落とすと: 失敗してもログに残るだけで、誰も気づかないまま日が経つ。
- 質問の例: 「この処理が失敗し続けたら、誰が、いつ、何で気づきますか」
- テスト: 通知や記録が仕様なら、統合テストで確かめる(例: 3 回失敗したらオペレーターに通知される)。

## 記録と説明

- 気づくきっかけ: 抽選、審査、自動の判定、料金の決定など、利用者から「なぜこの結果か」を問われうる処理。乱数を使う処理。
- 見落とすと: 結果だけが残り、なぜそうなったかを後から説明も再現もできない。問い合わせや監査に答えられない。
- 質問の例: 「この結果について問い合わせが来たら、何を見て説明しますか。どれくらいの期間さかのぼれる必要がありますか」
- テスト: 判定に使った入力(乱数のシード、その時点の設定の版)を記録し、同じ入力から同じ結果になることを単体テストで確かめる。

## テスト設計の悪手

計画のテストケース一覧そのものを点検する観点。[テスト戦略](../../../docs/testing-strategy.md) に照らす。

| 悪手 | なぜ悪いか | 直し方 |
|---|---|---|
| 業務ルールをフロントエンドで判定する | バックエンドと二重の実装になり、ずれる。API を直接呼ぶと素通りする | 判定はバックエンドのドメインに置く。フロントは表示だけ |
| 1 つのパラメータ化テストの軸が 3 つ以上 | 状態や種類が 1 つ増えると、ケースが掛け算で増える | 種類で先に分け、判断を小さな関数に分ける(4 章の 1〜4) |
| 入力の直積を全部テストにする | 「どちらでもよい」条件まで展開して、読めない量になる | 仕様上意味のある組み合わせごとに 1 ケースにする |
| 実装の詳細(呼んだ回数、内部の関数)を確かめる | リファクタリングで壊れる。振る舞いは守られていない | 観察できる結果(戻り値、保存された状態、外に出た通知)を確かめる |
| 自分のアプリだけが使う DB をモックにする | 制約やトランザクションの誤りを見逃す | 管理下の依存は本物を使う。モックは管理外の依存だけ |
| ハッピーパスの統合テストを何本も書く | 遅く、同じことを何度も確かめている | シナリオごとに最長のハッピーパスを 1 本。残りは単体と、単体では確かめられない異常系 |
| なぜに結び付かないテスト | 誰も理由を説明できず、消してよいか判断できない | なぜを足すか、削る |
