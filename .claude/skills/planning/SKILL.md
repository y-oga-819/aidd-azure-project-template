# プランニング

ストーリーから計画を作り、人間のゲート 1(計画のレビュー)に渡すまでを行う。
流れの全体は [docs/development-flow.md](../../../docs/development-flow.md)、前提の判断は [ADR-0005](../../../docs/adr/0005-tests-as-specification.md)(仕様の正本はテスト、計画は使い捨て)にある。

## この skill の狙い

- **悪手に気づくのを経験頼みにしない。** 見落としやすい観点を AI が持ち込み、質問にして人間に判断してもらう。観点の一覧は [checklist.md](checklist.md)。
- **質問には必ず「なぜ聞くか」を添える。** 何を見落とすと何が起きるかを知れば、次からは人間が自分で同じところに着目できる。若手が学ぶ場にもする。
- **why と期待値は人間が決める。** AI は材料集め、洗い出しの表、観点、仮の答えまでを出す。AI が全部埋めた計画は、レビューしても誰も判断していないのと同じになる。
- **コードを書く前に直す。** 計画の誤りは、テストや実装を書いた後より、今直す方が安い。

## 進め方

### 0. 規模を見分ける

- 「〜なら拒否する」程度の小さな変更は、計画の 1(なぜ)と 4(テストケース一覧)だけを書く。質問も、なぜの確認と観点で引っかかったものだけにする。
- 迷ったら通常の規模で進める。省いた節は「省略(小さな変更のため)」と書く。

### 1. 材料を集める(聞く前に調べる)

コードや文書を読めば分かることは人間に聞かない。調べた上で「〜と理解しました。違えば教えてください」と確認の形にする。

- ストーリーの本文。リンクなら開いて読む。無ければ最初に聞く。
- 現在の仕様: `mise run docs:spec <絞り込み>`(機能名やテスト ID の接頭辞で絞る)。動かせない環境では `backend/tests/` などを読む。
- 関係するコード、機能ごとの README(`features/<機能>/README.md`)、ADR。
- `docs/plans/` にある過去の計画は経緯であり、今の仕様の根拠にしない。今の仕様はテストから引く([ADR-0007](../../../docs/adr/0007-plan-location.md))。

### 2. なぜを確かめる(最初の質問)

ストーリーから「誰の、どんな困りごとを解決するか」を 2〜3 行で下書きし、最初に人間に確かめる。
なぜがずれていると、以降の洗い出しが全部ずれるため。なぜはテストの docstring と PR 概要に引き写される。

### 3. 複雑さの種類を見分け、洗い出しの表を作る

テンプレートの 2-1 の表で種類を見分け、種類ごとの方法(決定表、状態遷移表、計算例、失敗の種類、境界の日時)で組み合わせを全部書く。

- 表の全マスを埋めようとする。**AI が根拠を持って埋められないマスは、質問にする。** 空欄が質問の一番の出どころになる。
- 全組み合わせを書いてから、答えが同じものをまとめる。まとめた理由は 2-3 に書く(人間がレビューする)。
- どの種類にも当たらない変更(構成、基盤、ルーティングなど)は、2-1 に「該当なし」と書き、checklist.md の「構成・基盤」の観点で洗い出す。2-2 には、届くリクエストの種類(パスの種類など)ごとに「返すもの」を並べた表を書く。
- フレームワークやライブラリの選定を含むストーリーでは、選定を最初の質問にする。後から替えると全部のテストと実装を書き直すことになり、次の作業者も同じ議論をするので、答えは ADR に残す判断になる。

### 4. 悪手の観点で点検する

[checklist.md](checklist.md) の観点を、**気づくきっかけ(ストーリーやコードに現れる兆し)がある分だけ** 当てる。
全観点を毎回質問すると、人間が読まずに答えるようになり、質問が形骸化する。当てなかった観点は聞かない。

### 5. 質問する

下の「質問の書き方」に従い、質問を全部作ってから、**1 問ずつ聞く。** 何問もまとめて出すと、答える人の負担が大きく、1 問ごとに考えなくなるため。

1. 最初に「質問は今のところ N 問」と数を伝える。
2. 重いものから 1 問ずつ、AskUserQuestion ツール(無い環境では、選択肢で答えられるカードや 1 問だけのメッセージ)で聞く。毎回「k 問目 / 残り M 問」を添える。
3. 回答を計画に反映するたびに、残りの質問を見直す。回答で答えが決まった質問は取り下げ、新しく出た疑問は足す。数が変わったら、次の質問でそう伝える(例: 「Q2 の回答で Q4 は不要になりました。残り 2 問」)。
4. 回答で表やテストケースが変わったら、どう変わったかを 2-4 の「影響」に書く。

### 6. 判断と捨てた案を書く

選択肢があった判断を、テンプレートの 3 の形(「ADR に残す判断」と「この PR だけの判断」、それぞれ採用と不採用)で書く。
線引きは「次の PR の作業者が知らないと、同じ議論を繰り返すか」。繰り返すなら ADR に残す判断にし、ADR の下書きを提案する([docs/adr/README.md](../../../docs/adr/README.md))。

### 7. 層を割り当て、テストケース一覧を書く

- 層は [テスト戦略](../../../docs/testing-strategy.md) の 2〜3 章に従う。複雑な判断はドメインの純粋関数(単体)、外部依存の失敗・DB 制約・冪等性は統合、主要な導線だけ E2E。
- フロントエンドに業務ルールを置く計画にしない。判定はバックエンドが正本。
- グループごとに「網羅の軸」を 1 行書く。何が抜けているかに気づけるようにするため。
- 「増えなかったもの」を書く。影響しそうに見えて新しいテストが要らないものと、その理由。
- 書き方の約束は下の「テストケース一覧の書き方」。

### 8. PR を分ける

共有される部分(状態の追加、DB スキーマ、API 契約)を最初の小さな PR にし、その後を並行できるように分ける。
未決の質問に依存しない部分を先に進められるようにする。

### 9. 自己点検して、人間に渡す

下の「渡す前の自己点検」を行い、計画ファイルを書いて人間に渡す。**テストや実装は書き始めない。** 書くのはゲート 1 を通った後。

## 質問の書き方

1 問ごとに次の形にする。

```markdown
### Q3. 与信の解放が決済代行側で失敗したら、注文はどうなりますか？

- なぜ聞くか: 外部依存の呼び出しは必ずどこかで失敗する。失敗時の振る舞いを決めないと、実装が黙ってエラーを握りつぶすか、無限にやり直す。ここが決まらないと、統合テストの異常系が書けない。(観点: 外部依存の失敗)
- AI の仮の答え: 3 回やり直し、それでも失敗したらオペレーターに通知する。根拠: 既存の売上確定の失敗と同じ扱い(PAYMENT-5)
- 答えで変わること: 統合テストが 1 本増えるか。通知の仕組みを PR に含めるか
```

- **「なぜ聞くか」は、見落としたときに何が起きるかを具体的に書く。** 「重要なので」では学びにならない。最後に観点の名前を括弧で書き、checklist.md と結ぶ。
- **仮の答えには根拠を書く。** 既存のテスト ID、ADR、コードの場所。根拠がなければ「推測」と書く。根拠のない仮の答えに同意されると、誰も判断していない仕様ができる。
- **答えで変わることを書く。** 答える人が、どれだけ重い質問かを判断できるようにするため。何も変わらない質問は出さない。
- **順番は重いものから。** (1) 答え次第でテストケースや PR の分け方が変わるもの、(2) 元に戻しにくいもの(データ、公開している契約、セキュリティ境界)、(3) その他。
- **選択肢で答えられる形にする。** 仮の答えを推奨の選択肢にし、「任せる」で答えられるようにする。ツールで聞くときも「なぜ聞くか」は質問文に含める。

回答の扱い:

| 回答 | 計画への書き方 |
|---|---|
| 人間が答えた | そのまま回答欄に書く |
| 「任せる」「仮の答えでよい」 | 「AI の案を採用(<仮の答え>)」と書く。人間が判断していないことがレビューで分かるように |
| 分からない、今は決められない | 「未決(<誰に聞けば決まるか>)」と書き、PR の分割で後回しにできるようにする |

## 学習モード

人間が「学習モード」「若手向けに」などと頼んだときは、気づく練習を優先する。速さは落ちる。

1. AI の観点を見せる前に、人間に「この変更で壊れそうなところ、決まっていないところ」を挙げてもらう。
2. 人間の答えと AI の観点を突き合わせる。人間が挙げなかった観点ごとに、なぜ見るべきかと、どこを見れば気づけたか(checklist.md の「気づくきっかけ」)を返す。
3. 質問では仮の答えを先に見せない。人間が答えてから、AI の考えと違う点を伝える。

## 計画ファイル

- 置き場所: `docs/plans/<ストーリーの短い英語名>.md`([ADR-0007](../../../docs/adr/0007-plan-location.md))。テンプレートをコピーして埋める。
- テストや実装と同じ作業ブランチでコミットする。PR 概要からリンクする。
- マージした後は更新しない。続きの変更は新しい計画にする。

### テストケース一覧の書き方

`mise run plan:verify` が機械で照合できる形にする(読み取りの仕組みは `tools/src/aidd_spec/plan.py`)。

- 照合の対象は、見出しに「テストケース一覧」を含む節の中にある、ヘッダーに `ID` 列を持つ表。列は `ID`、`テスト名`、`状態` を必ず置く。
- **ID** は `<機能の正式名>-<番号>`(例: `ORDER-8`、`GIFT-CARD-3`)。接頭辞は略さない。既存の機能に足すときは、`docs:spec` で今の最大の番号を確かめてその続きにする。
- **テスト名** は振る舞いを平易な日本語で書く。パラメータ化テストなら param の id の ID より後ろ、それ以外なら関数名から `test_` を除いたもの。
- **値まで照合したい列** は、列名をテストのパラメータ名(引数名)に揃える。揃えない列(「入力」「期待」など)は人間が見て確かめる。
- **状態** は 新規 / 変更 / 既存 / 削除。既存のテストに影響しないなら一覧に載せず、「増えなかったもの」に書く。

書いたら `mise run plan:verify docs/plans/<名前>.md` を流す。この時点の正しい結果は次のとおり。

- 「新規」の行: 「テストがない」と出る(まだ書いていないので)
- 「既存」の行: 一致する。一致しなければ、ID かテスト名の写し間違い
- 「変更」の行: テスト名か値が違うと出ることがある。違いが計画どおりの変更なら正しい

`mise` が使えない環境では流せない。その場合は人間に渡すときにそう伝える。

## 渡す前の自己点検

1. ゲート 1 で人間が見る 3 点を、自分で先に見る: 洗い出しに漏れがないか(まとめた理由は正しいか)、既存のルールや外部依存との絡みを見落としていないか、期待値は正しいか。
2. どのテストケースも 1(なぜ)か質問の回答に結び付くか。結び付かないテストは削るか、なぜを足すかを人間に聞く。
3. 計画が既存の ADR と矛盾していないか。
4. **批判的に見直す。** 一番自信のない判断はどれか。捨てた案が逆転するのはどんな前提が変わったときか。見落としていそうな観点はどれか。

人間に渡すときは、計画ファイルのパスと一緒に、次の順で伝える。

- 未決の質問(誰に聞けば決まるか)
- 「AI の案を採用」にした回答(人間がまだ判断していないもの)
- 一番自信のない判断と、その理由

## やらないこと

- 計画の前にテストや実装を書き始めない。
- 今の仕様を計画に写して保守しない。計画の「現在の仕様」は `docs:spec` の出力を貼るだけにし、正本はテストに置く。
- Gherkin(`.feature`)で書かない(ADR-0005)。
- 観点の一覧を全部質問にしない。
